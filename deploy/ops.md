# Один сервер: бэкапы и мониторинг

Пока сервер один, задача не «отказоустойчивость», а две вещи попроще и
поважнее: **не потерять данные** и **узнать первым**, что что-то сломалось.
Всё ниже настраивается за полчаса и ничего не стоит.

Оба скрипта берут настройки из `.env` в корне проекта.

```env
# Твой Telegram id — куда приходят бэкапы и тревоги.
# Узнать: напиши @userinfobot, он ответит числом.
BACKUP_CHAT_ID=123456789

# Пароль от архива. Длинный и случайный, положи в менеджер паролей.
# Потеряешь — бэкапы превратятся в мусор, расшифровать их будет нечем.
BACKUP_PASSPHRASE=…

# Необязательно: адрес «я жив» от healthchecks.io или Better Stack.
HEARTBEAT_URL=https://hc-ping.com/…
```

## Бэкапы

```bash
chmod +x deploy/backup.sh deploy/watchdog.sh
crontab -e
```

```cron
17 4 * * *  /srv/botfactory/deploy/backup.sh   >> /var/log/bf-backup.log 2>&1
*/5 * * * * /srv/botfactory/deploy/watchdog.sh >> /var/log/bf-watchdog.log 2>&1
```

Раз в сутки в 04:17 UTC скрипт снимает дамп базы, сравнивает его с прошлым
и, **если ничего не изменилось, не делает ничего** — ни архива, ни
сообщения. Изменилось — собирает архив из базы, загруженных файлов и `.env`,
шифрует и присылает тебе в Telegram. На сервере хранятся последние 14 штук.

Три вещи, которые стоит понимать про этот архив:

**В нём лежит `.env`, а в нём `FERNET_KEY`.** Без этого ключа дамп базы
бесполезен: токены ботов и ключи от касс зашифрованы им и расшифровать их
будет нечем. Поэтому архив всегда зашифрован, и без `BACKUP_PASSPHRASE`
скрипт просто не запустится.

**Копия на том же сервере — не копия.** Умер диск — умерли обе. Отправка в
Telegram нужна именно для этого: копия оказывается вне сервера и сразу у
тебя на телефоне.

**Потолок — 50 МБ.** Столько Telegram принимает от бота. Когда архив
подойдёт к 45 МБ, скрипт напишет, что пора заводить S3, и не станет молча
ничего не отправлять.

### Проверь восстановление сегодня, а не в день аварии

Бэкап, из которого ни разу не восстанавливали, — это надежда, а не бэкап.
Займёт десять минут:

```bash
# 1. Распаковать (спросит пароль). mkdir обязателен: tar не создаёт
#    каталог сам и падает с «Cannot open: No such file or directory».
mkdir -p /tmp/restore-test
openssl enc -d -aes-256-cbc -pbkdf2 -iter 200000 \
  -in botfactory-2026-09-24_04-17.tar.gz.enc | tar xz -C /tmp/restore-test

# 2. Поднять чистую базу рядом и залить дамп
docker run -d --name restore-test -e POSTGRES_PASSWORD=x -p 5433:5432 postgres:16-alpine
sleep 5
docker exec -i restore-test psql -U postgres -c 'CREATE DATABASE botfactory'
docker exec -i restore-test psql -U postgres botfactory < /tmp/restore-test/db.sql

# 3. Убедиться, что боты и заказы на месте
docker exec -i restore-test psql -U postgres botfactory \
  -c 'SELECT count(*) FROM bots; SELECT count(*) FROM payments;'

# 4. Убрать за собой
docker rm -f restore-test && rm -rf /tmp/restore-test
```

Если цифры сошлись с боевыми — бэкап рабочий. Повторяй раз в пару месяцев.

## Мониторинг

Сторож раз в пять минут проверяет четыре вещи и пишет в Telegram **только
когда состояние меняется** — упало и починилось. Иначе «кончается диск»
пришло бы 288 раз за сутки, и на третий день их перестали бы читать ровно
перед тем, как случится что-то настоящее.

| Проверка | Почему она тут |
|---|---|
| `/health` | Ходит в базу, а не отвечает константой. Мёртвая база = боты не принимают оплату. |
| Контейнеры | `restart: unless-stopped` не спасает от контейнера, который падает по кругу. |
| Место на диске | Самая частая смерть маленького сервера, и выглядит она как что угодно, только не как кончившееся место. |
| Свежесть бэкапа | Бэкап тихо перестал делаться — узнать об этом хочется заранее. |

### Чего сторож не умеет

Он работает на том же сервере. **Выключился сервер — сторож молчит.**
Тишина от него не значит «всё хорошо».

Это закрывается внешним «пульсом»: при каждой успешной проверке сторож
дёргает `HEARTBEAT_URL`. Перестали приходить сигналы — внешний сервис
напишет сам. Бесплатного тарифа healthchecks.io или Better Stack хватает с
запасом, настройка — пять минут, и только эта пара закрывает оба случая:
«упало приложение» и «упал сервер».

Пульс отправляется **только когда все проверки прошли**. Иначе внешний
сервис считал бы сервер здоровым ровно в тот момент, когда он не здоров.

## Перед тем как включить цену

Пока `PUBLICATION_PRICE_MINOR` равен нулю, сервис ничего не берёт и ничего
никому не обещает. В тот момент, когда цена становится ненулевой, к нему
появляются вопросы, на которые отвечает не код:

| Что | Где | Почему без этого нельзя продавать |
|---|---|---|
| `LEGAL_NAME`, `LEGAL_ID` | `.env` | Пока они пусты, `/legal/offer` и `/legal/privacy` отдают 404, а ссылок на них в подвале нет. Оферта, подписанная никем, хуже отсутствующей. |
| `LEGAL_ADDRESS` | `.env` | Спрашивает эквайер при подключении. |
| `SUPPORT_TELEGRAM` | `.env` | Пусто — в подвале показывается мета-бот. Живой человек отвечает быстрее. |
| Юрист прочитал оферту | — | Текст в `app/routers/legal.py` — шаблон. Цены в него подставляются те же, по которым выставляется счёт, но юрисдикция у каждого своя. |

Проверить, что всё на месте, можно одной командой — она должна вернуть
`200` дважды и показать название:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://your-domain.com/legal/offer
curl -s -o /dev/null -w '%{http_code}\n' https://your-domain.com/legal/privacy
curl -s https://your-domain.com/api/config | python3 -m json.tool | grep legal
```

## Обновление до образа без root

Контейнер `api` теперь работает от пользователя `app` (uid 10001), а не от
root. Новая установка ничего делать не должна. Но том `media_uploads`,
созданный раньше, принадлежит root, и без правки прав загрузка файлов
начнёт отвечать 500. Один раз после обновления:

```bash
docker compose run --rm --user root --entrypoint chown api -R 10001:10001 /srv/media_uploads
docker compose up -d
```

Проверка: `docker compose ps` должен показывать `api` как `healthy`.

## Ограничение частоты запросов

`nginx/default.conf` ограничивает вход (`/api/auth/`, 5 запросов в секунду
с адреса), остальной API (30/с) и уведомления платёжных систем (20/с).
Лимит считается по настоящему адресу клиента: nginx доверяет
`X-Forwarded-For` только из частных сетей (Caddy, внешний nginx, docker).
Если перед сервером стоит CDN с публичными адресами, добавь их в
`set_real_ip_from`, иначе лимит будет общим на всех посетителей.
