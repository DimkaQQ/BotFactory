General Information
Integration is the process of connecting two or more services using an API. It allows systems to exchange data and events, enabling them to work together in an automated and coordinated way.

With lava.top, you can set up integration with any external system, service, website, or Telegram bot — to accept and track payments, manage access, and control subscription statuses. This makes your workflows simpler and more convenient.

Key Terms:
Public API
Public API — lava.top's public programming interface that allows external software and applications to interact with each other over the network.

API Key
API Key — a unique code used for the authorization and authentication of an API client. Think of it as a login and password, but for software — without it, you can't access the data or features provided by the API.

Webhook
Webhook — a mechanism that allows one service to automatically send data to another in response to certain events. In simple terms, it’s a notification your system receives when something happens. Instead of constantly asking the server “what’s new?”, you configure a URL once, and the server notifies you when needed.

Refund
Refund — a full or partial return of funds to the customer for a completed sale. Initiated by the creator, support, or the system. The refunded amount is debited from the creator's balance; the platform fee is not returned.

Chargeback
Chargeback — a payment dispute raised by the customer through their bank. Initiated outside the platform. By the time we receive the dispute, the amount and the provider fee have already been debited from the creator's balance.

Getting started
To get started with integrating your service on the platform, you need to create an API key and set up a webhook.

1
How to Create an API Key
Go to Integrations section, choose Public API.
screenshot1.png

Click Create API Key.
screenshot1-1.png

The platform will generate the key automatically — copy it and save it securely on your device.
screenshot2.png

2
How to Set Up a Webhook
Create an API key and confirm that you’ve saved it.
Click the Add Webhook button.
screenshot3.png

Fill in the following fields:
URL — the endpoint on your server where webhook data will be sent (this is the address that will receive and process requests).
Event type:
payment.success — Successful payment
payment.failed — Failed payment
subscription.recurring.payment.success — Successful subscription renewal
subscription.recurring.payment.failed — Failed subscription renewal
subscription.cancelled — Subscription cancelled
refund.success — Successful refund
chargeback.initiated — Chargeback request received
screenshot13.png

A single webhook receives any set of events — select the ones you need from the list. You do not need a separate webhook per event. If it suits your setup, you can split events across URLs: payments to one address, refunds and chargebacks to another.

The "Successful refund" and "Chargeback request received" events are delivered only if selected. Before enabling them, make sure your handler returns 2xx for any event, including ones it does not recognise.

Choose an authentication method:
Basic - enter the login and password for your service that will receive webhook requests.
screenshot5.png

Your service’s API key - enter the API key of your service that will receive the webhook requests. Maximum key length: 80 characters.
screenshot6.png

Basic authentication: lava.top will send webhook requests to the specified URL using HTTP Basic Authentication. The request will be sent in the format: user:pass@example.com. Only HTTPS connections are allowed for this type of request to ensure security.

API Key Authentication: lava.top will send webhook requests to the specified URL, authenticated using an API key.The receiving server must extract the key from the HTTP header: "X-Api-Key".

Click the three dots next to the desired key and select Add Webhook.

Requirements for values:

If at least one of the values does not meet these requirements, the invoice is not created and a 400 error is returned. Partial saving is not supported.
2
How a customer returns to your page
After payment, the customer first returns to a lava.top page and is then redirected to your address.

The intermediate page shows a loading indicator and does not repeat the payment status — the customer has already seen it in the payment form and will see it on your page.

If no address was passed for that outcome, the customer stays on our page and sees the final status, as before.
3
Routing based on payment outcome
Payment confirmed
Target: successful_return_url

If not passed: Final status on the lava.top page

Payment failed
Target: failure_return_url

If not passed: Final status on the lava.top page

Payment cancelled
Target: cancel_return_url

If not passed: failure_return_url, if passed, otherwise the final status

We report a cancellation separately where the payment provider distinguishes it from a decline. Some providers do not — in those cases the customer is sent to failure_return_url. This is expected behaviour.
4
Queries in the return URL
We add two parameters to your address:

invoiceId — The invoice ID
status — success / failed / cancelled
Your own query parameters are preserved; ours are appended with &. If the address contains a fragment (#), the parameters are added before it.

Example: https://school.example.com/thanks?utm_source=lava becomes https://school.example.com/thanks?utm_source=lava&invoiceId=3fa85f64-5717-4562-b3fc-2c963f66afa6&status=success.

The status parameter is not a payment confirmation and must not be used to grant access to content.
It is a value in the address bar and can be forged on the customer's side. The source of truth for the payment state is the payment.success webhook and the GET /api/v1/invoices/{id} method.

No customer personal data is passed in the return URL. Email and other data are not added to the parameters: the address bar ends up in logs, browser history, and the referer header.

Restrictions
Applies only to invoices created via the API. Does not apply to direct sales on lava.top
For subscriptions, applies only to the first payment. Renewals run without a browser session
If the automatic redirect fails, the customer stays on our page and sees a link to continue manually

Clients and API Keys
Lava.top uses two types of API keys, each serving a specific role in the integration process:

API Key for signing requests to lava.top
This key is used by your system to send API requests to lava.top. It allows us to identify and authorize your application.

API Key for signing webhooks from lava.top
This key is generated on your side and shared with lava.top. The platform uses it to sign webhook requests by adding it to the X-Api-Key HTTP header when sending data to your server.

Both keys are essential to ensure a secure and reliable integration between your system and lava.top.
Errors
Lava.top uses standard HTTP response codes to indicate whether an API request was successful or if an error occurred.

All outgoing connections originate from the IP address 158.160.60.174

Important: Please make sure to whitelist this IP on your side!
Retry Policy
If the webhook is not delivered, the system will automatically try to resend it to the specified URL. The first attempt will be in one second, the second in five seconds, and the third in 15 seconds. The system will then make ten attempts with an interval of one minute. After that, if unsuccessful, the system will make five more attempts with an interval of one hour.

Up to 20 attempts will be made in total.

The most common errors:

Code	Descriprion
400	Bad Request: the request is malformed. Check the syntax, parameters, and size limits. When creating an invoice, this error is also returned if a return URL does not use https, is not an absolute URL, or exceeds 512 characters.
401	Unauthorized: Authentication error. Verify your API key, OAuth token, token expiration, or required scopes.
403	Forbidden: Access to the resource is denied. You may lack permissions or be trying to access a restricted resource.
404	Not Found: The resource was not found. Check the URL, object ID, or whether the resource exists in your account.
405	Method Not Allowed: The HTTP method is not supported for this endpoint. Refer to the API documentation.
406	Not Acceptable: Unsupported request or response format. The API only supports application/json.
408	Request Timeout: The server timed out waiting for the request to complete. Try resending with smaller data payloads.
410	Gone: The resource has been permanently deleted and is no longer available.
429	Too Many Requests: Rate limit exceeded. Reduce the frequency of requests.
500	Internal Server Error: A server-side error occurred. Try again later.
503	Service Unavailable: The service is temporarily unavailable due to maintenance or overload. Please try again later.
Rate Limits
Lava.top applies request rate limiting to protect against overload and ensure stable API performance.

50
Current limit: up to 50 requests per second per IP address.
If this limit is exceeded, the server will respond with an error code 429. In this case, it's recommended to wait before retrying the request.
For high-load services, feel free to contact our support team: support@lava.top

Each event is associated with a payment type and a contract status.

Payment Types:

one-time payment (purchasing a digital product, course, consultation, or the first payment in a subscription);

Contract Statuses:

success (payment was successful);

cancelled (the subscription was cancelled).
Based on this, you may encounter the following Event types:

payment.success — successful purchase of a product (not a donation) or the first subscription payment;

How to handle these events
Use event_id to guard against duplicate processing. It does not change between retries.
Delivery order is not guaranteed. Rely on event_id and created_at, not on the order in which events arrive.
A refund and a subscription cancellation are independent. A refund does not necessarily cancel the subscription.
Each partial refund produces a separate event with its own event_id and refund_id.
Return 2xx for any event type, including unknown ones.
If a refund or chargeback cancels the subscription, the subscription_cancelled field is set to true, and a separate subscription.cancelled event is also sent in the existing format.

To receive it, select "Subscription cancelled" in your webhook settings.

Do not process the same cancellation twice: use subscription_cancelled for an immediate reaction, and subscription.cancelled as the primary subscription lifecycle event, with its cancelledAt and willExpireAt dates.

Restrictions
We notify you when a dispute is opened. The chargeback outcome — won, lost, or withdrawn by the customer — is not reported via webhook.
A chargeback on a donate is sent even though refunds on donates are not allowed by the platform policy: a chargeback is initiated by the bank, not by the platform.
A refund is not possible on a transaction that has a chargeback. No refund.success event is sent for it.
If a chargeback follows a partial refund, the amount field contains the disputed remainder, not the full sale amount.
Webhook Status
The status indicates whether the webhook was successfully received.

screenshot14.png

A webhook can have one of two statuses:

DELIVERED — the webhook was successfully delivered.
FAILED — the webhook delivery failed.
The status is determined based on the HTTP response code returned by your server when the event is sent.

An event is considered delivered if your service responds with a 2xx code within 10 seconds. If no response is received within that time, the attempt is treated as failed and the event is retried according to the general retry policy.
Retry Policy
Lava.top uses HTTP status codes to determine whether an API request was successfully processed or failed.

If a webhook delivery fails (i.e., a non-successful HTTP status code is returned), lava.top will retry the delivery up to 19 additional times, for a total of 20 attempts.

If webhooks were not delivered, the system will attempt to resend them to the specified URL. Repeated attempts are made according to the logic: first 1s, 5s, 15s, then 10 attempts with an interval of 1 min, then, if unsuccessful, another 5 attempts with an interval of 1 hour.

In total, 20 delivery attempts will be made.

Each attempt is logged in the webhook history with the corresponding HTTP status code. If a successful status code is received, no further retries will be made. In that case, you’ll see only one event logged (successful or failed payment).

In case of an unsuccessful response, up to 20 attempts may be made (retries stop after a successful delivery or after 19 retry attempts).

You can view all retry attempts in the "Sending attempt history" section of the webhook details.

screenshot15.png

Most common response codes:

Code 401 / Code 403 — Invalid authentication data; access to the webhook handler is denied;
Code 404 — The webhook contains an incorrect URL (the link to the author's server that receives and processes the webhook is invalid)
Code 500 — An error occurred on the author's server that is responsible for handling the webhook.
