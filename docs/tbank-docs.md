Сборка: 5 октября 2026. Нужный вариант интеграции: **редирект на платёжную форму банка через API** (сервер вызывает `Init`, клиент уходит на `PaymentURL`, итог приходит на `NotificationURL`).

Страницу Init (https://developer.tbank.ru/eacq/api/init) автоматически открыть нельзя (сайт запрещает чтение роботам), поэтому **полный текст Init взят из страницы, которую вы прислали**: это точные требования к полям и ответу. ## 1. Адрес и общие правила

- Тело запросов JSON.
- Запросы к API только **со своего сервера**.
- Все методы подписываются полем `Token` (раздел 3).
- Ответ банка с `Success: false` — **нормальный результат, а не исключение**: решения принимать по `ErrorCode`, `Message`, `Details`.
- **Боевая среда:** `https://securepay.tinkoff.ru/v2/<Метод>`.
- **Тестовая среда:** `https://rest-api-test.tinkoff.ru/v2/<Метод>`. Среды **изолированы** друг от друга, **пароли терминалов в них совпадают**.
- Два способа тестировать (подтверждено страницами «Тест-кейсы» и FAQ «Что проверить перед запуском платежей»):

| Способ | Терминал | Хост |
|---|---|---|
| Тест-кейсы из ЛК (необязательные) | **DEMO-терминал** (оканчивается на `DEMO`) | **боевой** `securepay.tinkoff.ru` |
| Тестовые платежи перед запуском | **боевой терминал без приставки DEMO** | **тестовый** `rest-api-test.tinkoff.ru` |

- Тестовые карты работают только в тестовой среде, реальные карты на тесте не работают, а тестовые на бою.
- Решение для кода: **хост — настройка кассы**. Режим «тест» = тот же `TerminalKey` и пароль + `rest-api-test.tinkoff.ru`; режим «бой» = `securepay.tinkoff.ru`. DEMO-терминал с боевым хостом нужен только для тест-кейсов из ЛК.

### Правила работы (страница «Введение», версия документации 1.36)

- Параметры передаются **POST в формате JSON**, заголовок `Content-Type: application/json`.
- **Все методы и параметры чувствительны к регистру.**
- TLS **1.2 и выше**.
- В строковых значениях **избегать символов `'`, `"`, `&`, `<`, `>`** или экранировать их. Часть параметров в уведомлениях тоже может приходить экранированной.
- Для большинства методов нужна подпись `Token`.
- Оплата **только в рублях**. Если нужна валюта, конвертацию суммы мерчант делает у себя до запроса.

⚠ Для адаптера: в `Description`, `Name` позиций чека и значениях `DATA` не оставлять `&`, `<`, `>`, кавычки (например, названия вроде «Бот "Магазин" & Co»), иначе возможны ошибки. Для проверки `Token` уведомления использовать значения **как они пришли**; если в строках встречаются экранированные символы, проверку подписи тестировать на реальном уведомлении (в доке про это нет подробностей, это мой вывод из фразы про экранирование).

## 2. Метод Init: создание платежа (полная схема, официальная страница)

### Запрос

| Параметр | Обяз. | Тип и ограничения | Описание |
|---|---|---|---|
| `TerminalKey` | да | string, ≤ 64 | Идентификатор терминала |
| `Amount` | да | int64 | **Сумма в копейках** (3 руб. 12 коп. = `312`). Должна равняться сумме всех `Amount` в `Items` чека. Минимальная сумма через СБП — **10 руб.** |
| `OrderId` | да | string, ≤ **50** | Идентификатор заказа, **уникален для каждой операции**. При оплате цифровым рублём — до 35 знаков. В реестре банка номер заказа: «цифры, буквы, кроме спецсимволов» (раздел 26), поэтому использовать **только `A-Za-z0-9`** |
| `Token` | да | string | Подпись запроса (раздел 3) |
| `Description` | нет | string, ≤ **140** | Описание заказа, отображается на платёжной форме. При оплате картой — до 250 символов; при СБП и платежах по сохранённым реквизитам — до 140. Обязателен при привязке и одновременной оплате через СБП (текст виден в мобильном банке) |
| `CustomerKey` | условно | string, ≤ 255 | ID покупателя у нас; нужен для сохранения карт на форме («в один клик»). **Обязателен**, если `Recurrent=Y` и автоплатёж по карте. Если передан, в уведомлении придут `CustomerKey` и `CardId` |
| `Recurrent` | нет | string, единственное значение `Y` | Признак родительского CC-платежа: сохранить реквизиты карты. После оплаты в уведомлении `AUTHORIZED` придёт **`RebillId`** для метода «Провести платёж по сохранённым реквизитам». Для привязки с одновременной оплатой по СБП тоже `Y` |
| `PayType` | нет | `O` или `T` | `O` — одностадийная, `T` — двухстадийная. Если не передан, берётся из настроек терминала. ⚠ Не должен противоречить настройке терминала (раздел 20) |
| `Language` | нет | ≤ 2, по умолчанию `ru` | Язык платёжной формы: `ru` или `en` |
| `NotificationURL` | нет | uri | Куда POST-ом слать статусы. Если передан — он, иначе из настроек терминала |
| `SuccessURL` | нет | uri | Куда вернуть покупателя после успешной оплаты; иначе из настроек терминала |
| `FailURL` | нет | uri | Куда вернуть при неуспешной оплате; иначе из настроек терминала |
| `RedirectDueDate` | нет | date-time `YYYY-MM-DDTHH24:MI:SS+GMT`, пример `2016-08-31T12:28:00+03:00` | **Срок жизни ссылки** (или динамического QR СБП). Минимум — 1 минута от текущего момента, максимум — **90 дней**. Если дата меньше текущей, оплата по ссылке недоступна. Если не передан: берётся настройка терминала `REDIRECT_TIMEOUT` (в часах); если она > 0 — используется, если < 0 — по умолчанию **1440 минут (сутки)** |
| `DATA` | нет | object | Доп. параметры `ключ:значение` (сюда же кладётся `OperationInitiatorType`): не более **20 пар**, ключ ≤ **20** знаков, значение ≤ **100**; спецсимволы кодировать `urlencode` |
| `Receipt` | условно | object | Чек, **обязателен при подключённой онлайн-кассе** (раздел 6) |
| `Shops` | для маркетплейсов | array | Данные маркетплейса. Нам не нужен |

**`OperationInitiatorType` передаётся внутри `DATA`** (в примере запроса `"DATA": {"OperationInitiatorType": "0"}`, значение строкой). Допустимые значения подтверждены страницей «Платежи по сохранённым реквизитам» (раздел 7): `1` — родительский платёж, `2` — CIT COF, `R` — регулярный (подписка), `I` — по графику (рассрочка), `D` — отсроченное списание, `N` — плата за неявку. Для обычной разовой оплаты «Быстрый старт» формы банка тоже велит указать `OperationInitiatorType` в `DATA`; в примере `Init` стоит `"0"` (разовый платёж). Страница про сохранённые реквизиты `0` не перечисляет, поэтому передавать `"0"` по примеру и проверить на DEMO. Неверное значение даёт ошибку `1125`, несогласованное с `RebillId`/`Recurrent` — `1126`.

### Ответ (HTTP 200)

Схема `InitResponse` или `ErrorResponse`.

| Поле | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | ≤ 64 |
| `Amount` | да | int64, сумма в копейках |
| `OrderId` | да | ≤ 50 |
| `Success` | да | boolean, успешность **прохождения запроса** |
| `PaymentId` | да | string, ≤ **20** символов, идентификатор платежа в Т-Бизнес |
| `ErrorCode` | да | string, ≤ 20, код ошибки. `"0"` — без ошибки |
| `Status` | нет | Статус транзакции (список ниже) |
| `PaymentURL` | нет | uri, ≤ 100. **Ссылка на платёжную форму; возвращается только мерчантам, которые используют платёжную форму Т-Банка** |
| `Message` | нет | ≤ 255, краткое описание ошибки |
| `Details` | нет | подробное описание ошибки |

```json
{
  "Success": true,
  "ErrorCode": "0",
  "TerminalKey": "xxxxxxxxxxxxx",
  "Status": "NEW",
  "PaymentId": "999999999",
  "OrderId": "123",
  "Amount": 30000,
  "PaymentURL": "https://securepay.tinkoff.ru/new/xxxxx"
}
```

### Ответ при внутренней ошибке (HTTP 500)

Другая схема: `Success`, `ErrorCode`, `Message`, **`Causes`** (массив причин), `StackTrace`. Здесь `Message` и `ErrorCode` обязательны, `PaymentId` нет.

### Официальные примеры

Успешный ответ (200):
```json
{
  "Success": true,
  "ErrorCode": "0",
  "TerminalKey": "TBankTest",
  "Status": "NEW",
  "PaymentId": "3093639567",
  "OrderId": "21090",
  "Amount": 140000,
  "PaymentURL": "https://pay.tbank.ru/new/fU1ppgqa"
}
```
Домен `PaymentURL` в примере — `pay.tbank.ru`. В старых примерах встречается `securepay.tinkoff.ru/new/...`. Не зашивать домен в проверки, ссылку брать из ответа как есть.

Внутренняя ошибка (500):
```json
{
  "Success": false,
  "ErrorCode": "9999",
  "Message": "Внутренняя ошибка системы.",
  "Causes": ["Internal Service Error."]
}
```
`ErrorCode` `9999` — внутренняя ошибка системы. Отказ с HTTP 200 и `Success: false` приходит в другой форме (раздел «Ответ»).

Запрос на Python (из документации, сокращённо до нужного нам):
```python
import http.client, json

conn = http.client.HTTPSConnection("securepay.tinkoff.ru")   # тест: rest-api-test.tinkoff.ru
payload = json.dumps({
    "TerminalKey": "TBankTest",
    "Amount": 140000,
    "OrderId": "21050",
    "Token": "<подпись>",
    "Description": "Подарочная карта на 1400.00 рублей",
    "PayType": "O",
    "Language": "ru",
    "NotificationURL": "https://example.com/tbank/notify",
    "SuccessURL": "https://example.com/success",
    "FailURL": "https://example.com/fail",
    "RedirectDueDate": "2026-10-02T17:42:43+03:00",
})
conn.request("POST", "/v2/Init", payload,
             {"Content-Type": "application/json", "Accept": "application/json"})
print(conn.getresponse().read().decode("utf-8"))
```
(`"Recurrent": "Y"`, `"CustomerKey"`, `"DATA"` в этот пример добавляются только для сохранения карты и автоплатежей.)

⚠ Для адаптера:
- Успех = `Success == true` **и** `ErrorCode == "0"` **и** есть `PaymentURL`. Ответ с `Success: false` — это не исключение, а штатный отказ, разбирать `Message`/`Details`.
- HTTP 500: тело другое (пример: `ErrorCode: "9999"`, `Causes`), **не** искать там `PaymentId`. После сбоя или таймаута `Init` результат неизвестен: проверять через `CheckOrder` по `OrderId` (раздел 13). **Ни `CheckOrder`, ни `GetState` не возвращают `PaymentURL`**, поэтому ссылку для уже созданного платежа восстановить нельзя. Если платёж существует (`NEW`), а ссылки у нас нет, создавать новый платёж с новым `OrderId` (например `ord123r2`), а брошенный не использовать.
- `PaymentURL` может **отсутствовать**, если у мерчанта не включена платёжная форма банка. Нужна явная ошибка «у терминала не включена платёжная форма», а не падение на `KeyError`.
- `OrderId` ≤ 50 и **уникален для каждой операции**: для повторной попытки оплаты того же заказа нужен новый `OrderId` (например `ord123r2`), либо использовать тот же платёж, пока он жив.
- `PaymentId` строка до 20 символов (в уведомлении придёт числом).

## 3. Подпись Token (проверено расчётом)

Официальный алгоритм (страница «Токен»):
1. Собрать пары ключ-значение параметров запроса **только корневого уровня**. Вложенные объекты `Receipt` и `DATA` **исключаются**.
2. Добавить пару `{"Password": "<пароль терминала>"}`.
3. Отсортировать пары по **ключу по алфавиту**.
4. Склеить **только значения** в одну строку.
5. SHA-256 от UTF-8 строки → hex → поле `Token`.

Проверка по официальному примеру (терминал `MerchantTerminalKey`, пароль `11111111111111`, `Amount=19200`, `OrderId=00000`, `Description=Подарочная карта на 1000 рублей`): строка до хеша
`19200` + `Подарочная карта на 1000 рублей` + `00000` + `11111111111111` + `MerchantTerminalKey`,
результат `72dd466f8ace0a37a1f740ce5fb78101712bc0665d91a8108c7c8a0ccd426db2` совпал с токеном из доки.

⚠ В самой доке есть опечатка: итоговый JSON-пример показывает `OrderId: "21090"` с этим же токеном, а токен считается для `OrderId: "00000"`. Это ошибка примера, не алгоритма.

```python
import hashlib

def _s(v):
    if isinstance(v, bool):
        return "true" if v else "false"   # НЕ "True"/"False"
    return str(v)

def tbank_token(params: dict, password: str) -> str:
    flat = {k: _s(v) for k, v in params.items()
            if k != "Token" and not isinstance(v, (dict, list))}
    flat["Password"] = password
    return hashlib.sha256("".join(flat[k] for k in sorted(flat)).encode("utf-8")).hexdigest()
```

### Что входит в Token для полного запроса Init

В Token входят **только скалярные поля корневого уровня**: `TerminalKey`, `Amount`, `OrderId`, `Description`, `CustomerKey`, `Recurrent`, `PayType`, `Language`, `NotificationURL`, `SuccessURL`, `FailURL`, `RedirectDueDate` (в том виде, как переданы, строкой). **Не входят** вложенные объекты и массивы: `DATA`, `Receipt`, `Shops`. Значит `OperationInitiatorType` (он в `DATA`) в подпись не попадает. Любое поле, которое вы добавили в запрос, нужно учесть в подписи, иначе будет ошибка «неверный токен». Функция `tbank_token` выше как раз пропускает `dict` и `list`.

## 4. Статусы и стадийность

Полный список `Status` из схемы ответа Init (`SessionStatusEnum`):

| Статус | Значение |
|---|---|
| `NEW` | платёж создан |
| `FORM_SHOWED` | форма оплаты показана |
| `3DS_CHECKING` | идёт проверка 3DS |
| `3DS_CHECKED` | проверка 3DS завершена |
| `AUTHORIZED` | платёж авторизован (двухстадийная: ждёт подтверждения) |
| `CONFIRMED` | платёж подтверждён (деньги списаны) |
| `REVERSED` | платёж отменён |
| `REFUNDED` | возврат выполнен |
| `PARTIAL_REFUNDED` | частичный возврат |
| `REJECTED` | платёж отклонён |
| `DEADLINE_EXPIRED` | срок жизни платежа истёк |

Это список из схемы ответа Init. **Полный список из схемы ответа `Confirm` шире**, он приведён в разделе 10 (24 статуса, включая `AUTH_FAIL`, `CANCELED`, `CONFIRMING`, `COMPLETED`, `UNKNOWN`). После трёх неудачных попыток оплаты платёж переходит в `REJECTED`. Обрабатывать нужно оба набора, а неизвестный статус не должен ронять обработчик.

- Одностадийная: успех → `CONFIRMED` + редирект на `SuccessURL`; неуспех → `AUTH_FAIL`, после 3 попыток `REJECTED` + `FailURL`.
- Двухстадийная: успех → `AUTHORIZED` + `SuccessURL`. Холд на карте, по фрагменту страницы сценария из поиска, **до 7 дней** (правила НСПК), подтвердить нужно в течение 7 дней, **включая день авторизации**; у некоторых способов оплаты срок 30 дней. ⚠ **Конкретный срок по способам оплаты на присланных страницах (FAQ «Холдирование», `Confirm`) не указан**, и два источника расходятся: фрагмент сценария говорит, что по истечении срока платёж подтверждается автоматически (деньги спишутся), а FAQ говорит, что деньги на карте разблокируются. Не полагаться ни на то, ни на другое, а вызывать `Confirm` заранее. Уточнить у банка, что именно происходит по способам оплаты.
- Банк рекомендует после уведомления **сравнивать `Amount`** с ожидаемой суммой.

## 5. Уведомления (webhook): официальная страница

### Настройка и отправка

- ЛК интернет-эквайринга → **Магазины** → вкладка **Терминалы** → **Настроить** → способ получения: почта, HTTP(S) или оба.
- Для HTTP(S) передавайте `NotificationURL` в `Init`. Если параметр передан, используется он, иначе значение из настроек терминала.
- **Уведомления о привязке карты, фискализации и привязке счёта по QR приходят только на `NotificationURL` из настроек терминала**, параметр из `Init` на них не действует. Для привязки карты изменить адрес можно через персонального менеджера или поддержку.
- Допустим порт 443 (HTTPS).
- На почту Т-Бизнес присылает письма только об успешных платежах.

### Когда приходит уведомление

| Вызов | Уведомление |
|---|---|
| `Confirm`, `Cancel` | POST на `NotificationURL` |
| `FinishAuthorize` (своя форма), двухстадийная | POST на `NotificationURL` |
| `FinishAuthorize`, одностадийная | POST на `NotificationURL`, ответа ждут **10 секунд**; сервис **одновременно отправляет два уведомления: `AUTHORIZED` и `CONFIRMED`** |
| `Charge` | та же логика, что у `FinishAuthorize` |
| Привязка карты | POST на `NotificationURL`, ответа ждут 10 секунд |

⚠ Из этого следует: при одностадийной оплате вебхук может прийти **дважды** (`AUTHORIZED` и `CONFIRMED`), оплатой считать только `CONFIRMED`, а обработчик должен быть идемпотентен по `PaymentId` + `Status`.

### Ответ банку и повторы

- Вернуть **HTTP 200 с телом `OK`**: без тегов, заглавными английскими буквами. Любой другой ответ считается неуспешным.
- Повторы: **раз в час в течение 24 часов**, затем **раз в сутки в течение месяца**, после этого уведомление уходит в архив. В архиве хранится **90 дней**, в этот период можно запросить повторную отправку.

| `Status` | Статус платежа (список ниже) |
| `PaymentId` | ID платежа в Т-Бизнес |
| `ErrorCode` | Код ошибки |
| `Message`, `Details` | Описание ошибки; **не передаются в методе `FinishAuthorize`** |
| `CardId` | ID платёжного средства; может отсутствовать, если в `Pan` телефон |
| `Pan` | Маска карты или телефон |
| `ExpDate` | `MMYY`; пустой для привязок с `CheckType=NO`; может отсутствовать при оплате без карты |
| `RebillId` | В таблице страницы не перечислен, но участвует в официальном примере токена и приходит при `Recurrent=Y` |
| `Data` | Доп. параметры из `DATA` запроса (имя `Data`, **регистр важен**) |
| `Token` | Подпись |

Для СБП добавляются `Data.AccountToken`, `Data.sourceId`, `Data.bankName`, `Data.bankMemberId`, `Data.settlementDate`, `Data.operationDate`, `Data.paymentDate`, `Data.extQrId`, `Data.RefundTransactionId`, `Data.RefundOperationDate`; для цифрового рубля `Data.DrPaymentId`, `Data.DrPaymentSettlementDate`, `Data.ParticipantWalletId`. Нам не нужны.

Через `DATA` можно получать свои параметры (например `description`, `order_number`); дополнительные параметры `DATA` включаются через менеджера. `source` при платёжной форме банка возвращается автоматически, для платежа по сохранённым реквизитам его нужно передать в `DATA` в `Init`.

### Статусы платежа в уведомлении

| Статус | Значение |
|---|---|
| `AUTHORIZED` | Авторизовано, деньги заблокированы. Подтвердить: `Confirm` или ЛК |
| `CONFIRMED` | Подтверждено, деньги списаны |
| `PARTIAL_REVERSED` | Частичная отмена по авторизованной операции |
| `REVERSED` | Полная отмена по авторизованной операции |
| `CANCELED` | Отменена, когда была создана платёжная ссылка |
| `PARTIAL_REFUNDED` | Частичный возврат по подтверждённой операции |
| `REFUNDED` | Полный возврат по подтверждённой операции |
| `REJECTED` | Списание закончилось ошибкой |
| `DEADLINE_EXPIRED` | Платёж не прошёл 3DS в срок: сессия в `3DS_CHECKING` дольше **36 часов** закрыта автоматически (уведомление об этом включается через чат ЛК) |

Холд (FAQ «Как работает холдирование платежей?»): у каждого способа оплаты свой максимальный срок холда. **Если платёж не подтверждён методом `Confirm` в этот срок, деньги на карте покупателя разблокируются.** Сноска страницы уведомлений «По неподтверждённым операциям деньги не возвращаются» согласуется с этим, если читать её как «деньги по такой операции не списывались» (это моё прочтение). Срок холда по способам оплаты на присланных страницах не указан (раздел 4): планировать `Confirm` заранее и уточнить срок у банка.

### Проверка Token уведомления (проверено расчётом)

1. Взять **все переданные в уведомлении параметры** (не фиксированный список!), кроме `Token` и вложенных объектов (`Data`, `Receipt`).
2. Добавить `{"Password": "<пароль терминала из ЛК>"}`.
3. Отсортировать по ключу по алфавиту.
4. Склеить **только значения**.
5. SHA-256 (UTF-8) → сравнить с `Token`.

- Значение `null` в подписи **не учитывается** (пропускается).
- **`Success` участвует как `true`/`false` (строкой в нижнем регистре).**
- Официальный пример: строка `111100000001111000000200000******0000111111111110000000000000AUTHORIZEDtrue1234567890DEMO`, SHA-256 `1c0964277d0213349243065a0d5b838b8e90d2d25f740d0f2767836e710e80c8`. Я пересчитал, совпало.
- Для уведомления о привязке карты в подписи участвуют: `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId`, `Pan`, `ExpDate`, `NotificationType`, `RebillId` (если присвоен при привязке).
- Избегайте символов `'`, `"`, `&`, `<`, `>` в значениях: они экранируются в нотификациях.

### Уведомления о привязке карты

Поля: `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId`, `Pan`, `ExpDate`, `Token`. ⚠ Страница описывает `Status` так: «`COMPLETED` — при одностадийной оплате, `REJECTED` — при двухстадийной». Это явная неточность. Ориентироваться на `GetAddCardState`: `COMPLETED` — карта привязана, `REJECTED` — не удалось.

### Уведомление о фискализации

`Status` всегда `RECEIPT`. Поля: `TerminalKey`, `OrderId`, `Success`, `PaymentId`, `ErrorCode`, `ErrorMessage`, `Details`, `Amount`, `FiscalNumber`, `ShiftNumber`, `ReceiptDatetime`, `FnNumber`, `EcrRegNumber`, `FiscalDocumentNumber`, `FiscalDocumentAttribute`, `Receipt`, `Type`, `Ofd`, `Url` (копия чека), `QrCodeUrl`, `CalculationPlace`, `CashierName`, `SettlePlace`, `Token`. Приходит только на `NotificationURL` из настроек терминала. Полезно показать продавцу `Url` чека.

### Для адаптера (вебхук)

1. Проверить IP (желательно) и **`Token`** до любых действий.
2. Ответить `OK` быстро (до 10 секунд), тяжёлую обработку отложить.
3. Идемпотентность по `PaymentId` + `Status` (повторы раз в час 24 часа; на одностадийный платёж приходят `AUTHORIZED` и `CONFIRMED`).
4. Оплатой считать `CONFIRMED`. По `AUTHORIZED` двухстадийной оплаты вызвать `Confirm`.
5. Сверить `OrderId` и `Amount` с заказом, дополнительно `GetState` (раздел 12).
6. Статусы `REVERSED`, `PARTIAL_REVERSED`, `REFUNDED`, `PARTIAL_REFUNDED`, `CANCELED`, `REJECTED`, `DEADLINE_EXPIRED` — платёж не принесёт денег, обновить заказ.
7. Неизвестные поля и статусы не должны ломать обработчик, а неизвестные поля нужно включать в проверку подписи.

```python
def tbank_verify_notification(payload: dict, password: str) -> bool:
    given = payload.get("Token")
    if not given:
        return False
    return hmac.compare_digest(tbank_token(payload, password), given)
    # tbank_token: булево -> "true"/"false", None пропускается, dict/list (Data, Receipt) исключены
```

## 6. Чек 54-ФЗ

Структура `Receipt` из официального примера запроса:

```json
"Receipt": {
  "Items": [
    {
      "Name": "Наименование товара 1",
      "Price": 10000,
      "Quantity": 1,
      "Amount": 10000,
      "PaymentMethod": "full_payment",
      "PaymentObject": "commodity",
      "Tax": "vat10"
    }
  ],
  "Email": "a@test.ru",
  "Phone": "+79031234567",
  "Taxation": "osn",
  "Payments": {"Cash": 90000, "Electronic": 19200, "AdvancePayment": 0, "Credit": 0, "Provision": 0}
}
```

- `Receipt` обязателен, **если подключена онлайн-касса** (то же в `Confirm` и `Cancel`).
- Верхний уровень: `Items[]` (до **100** позиций), `Email` или `Phone` (**нужен хотя бы один**), `Taxation` (СНО: `osn`, `usn_income`, `usn_income_outcome`, `esn`, `patent`), необязательные `Payments`, `AddUserProp {Name, Value}`, `additionalCheckProps`.
- Позиция: `Name` (≤128), `Price` (копейки), `Quantity`, `Amount` (= `Price × Quantity`, копейки), `Tax`, `PaymentMethod` (по умолчанию `full_payment`), `PaymentObject`. Значения `PaymentMethod`: `full_prepayment`, `prepayment`, `advance`, `full_payment`, `partial_payment`, `credit`, `credit_payment`. Для услуги `PaymentObject` — `service`, для товара `commodity`.
- Для платёжных агентов и маркетплейсов есть `AgentData` и `SupplierInfo`, а также `Ean13` и `ShopCode`. **Нам не нужны**, если продавец не работает как агент.
- `Payments` (необязательный): `Cash`, `Electronic`, `AdvancePayment`, `Credit`, `Provision`. Если не передан, итоговая сумма чека идёт видом оплаты «Безналичный». Если передан, `Electronic` должен равняться `Amount` платежа, а сумма по всем видам оплаты равна сумме `Amount` позиций.
- `Tax`: `none`, `vat0`, `vat5`, `vat7`, `vat10`, **`vat22`**, `vat105`, `vat107`, `vat110`, **`vat122`**. Значений 20% и 20/120 в списке уже нет.
- `Receipt` в расчёт `Token` **не входит**.

⚠ Пример в самой документации внутренне несогласован: `Amount: 140000`, а позиция на `10000` и `Payments` на `109200`. В реальном запросе должно быть **`Amount` платежа = Σ `Items[].Amount` = Σ `Payments`** (если `Payments` передан).

Минимальный чек для оплаты услуги (наш случай):

```json
"Receipt": {
  "Email": "buyer@example.com",
  "Taxation": "usn_income",
  "Items": [{
    "Name": "Запуск бота",
    "Price": 99000, "Quantity": 1, "Amount": 99000,
    "Tax": "vat22",
    "PaymentMethod": "full_payment",
    "PaymentObject": "service"
  }]
}
```
(`Taxation` и ставку берём из настроек продавца; при `full_payment` не нужен чек зачёта предоплаты.)

## 7. Платежи по сохранённым реквизитам: типы операций и `OperationInitiatorType`

Источник: страница «Платежи по сохранённым реквизитам» (платёжная форма банка).

Сценарий из двух этапов:
- **CC, родительский платёж** (Credential-Captured): ввод реквизитов с их сохранением. Два вида: **CC-покупка** (обычная оплата, реквизиты сохраняются) и **CC-привязка** (проверка и сохранение без оплаты, деньги временно блокируются).
- **COF, дочерний платёж** (Credential-on-File): оплата по сохранённым реквизитам. В рамках одного родительского платежа можно проводить несколько дочерних.

Для CC-авторизации картой обязательна аутентификация (3-D Secure) или ввод CVV.

### Что передавать

| Операция | `Init` | Дальше |
|---|---|---|
| **CC-покупка** (родительский платёж) | `Recurrent=Y`, `CustomerKey`, `OperationInitiatorType=1` | как стандартный платёж; после авторизации в уведомлении `RebillId` |
| **CC-привязка** | вызвать `AddCard`, клиенту отдать ссылку на форму | `RebillId` в уведомлении или `GetAddCardState` |
| **CIT COF** (клиент сам инициирует, реквизиты не вводит) | `OperationInitiatorType=2` | `Charge` с `RebillId` |
| **MIT COF Recurring** (магазин списывает без клиента, **подписка**, без фиксированного графика) | **`OperationInitiatorType="R"`** | `Charge` с `RebillId` |
| MIT COF Installment (по графику, рассрочка) | `"I"` | `Charge` |
| MIT COF Delayed-Charge (отсроченное списание) | `"D"` | `Charge` |
| MIT COF No-Show (плата за неявку) | `"N"` | `Charge` |

Для нашего случая нужны три: **CC-покупка** (первый платёж, `1`), **MIT COF Recurring** (периодическое списание подписки, `"R"`) и, возможно, **CIT COF** (`2`, оплата «в один клик» привязанной картой).

### Последовательность COF-операции

1. `Init` с новым `OrderId` и `Amount` (+ `Receipt`, + `DATA.OperationInitiatorType`).
2. **Без перенаправления на `PaymentURL`** сразу `Charge` с `PaymentId` и `RebillId` (раздел 15).

### Условия

- **По умолчанию платежи по сохранённым реквизитам отключены.** На DEMO-терминале включить: acq_help@tbank.ru. На боевом: персональный менеджер. Если не включены, `Charge` вернёт ошибку **10** («Метод Charge заблокирован для данного терминала»).
- Нужен ECOM-терминал. Для `Delayed-Charge` и `No-Show` ещё требуется согласование с менеджером, и они возможны только если родительская CC-операция — покупка с подтверждением через `Confirm`; **привязка карты в роли родительской для них не подходит**.
- Стадийность: для CC-операций из ЛК или `PayType` в `Init`; для COF-операций тоже `PayType` либо настройка терминала по умолчанию (меняется через acq_help@tbank.ru). Для привязок стадийность не применяется.
- Сценарии подходят и при оплате T-Pay и Mir Pay.
- Автоплатежи через **СБП** отдельные: родительского платежа нет, вместо него привязывается счёт; только по API.

⚠ Согласованность с ошибками: при неверном `OperationInitiatorType` банк вернёт `1125`; при несоответствии `RebillId`/`Recurrent` значению — `1126`.

## 8. Что взять в `tbank.py` (минимум)

1. `POST /v2/Init`: `TerminalKey`, `Amount` (копейки, int), `OrderId`, `Description`, `NotificationURL`, `SuccessURL`, `FailURL`, `PayType`, при онлайн-кассе `Receipt`, `Token`.
2. Проверить `Success == true` и `ErrorCode == "0"`, сохранить `PaymentId`, отправить клиента на `PaymentURL`.
3. Принять POST на `NotificationURL`, проверить IP и `Token` (раздел 5), сверить `OrderId`/`Amount`, при `Status == CONFIRMED` отметить оплату, ответить `OK` (HTTP 200, тело `OK`). При двухстадийной оплате по `AUTHORIZED` вызвать `Confirm` (раздел 10) и отметить оплату только после `CONFIRMED`. При одностадийной оплате приходят оба: `AUTHORIZED` и `CONFIRMED`.
4. После уведомления запрашивать `GetState` по `PaymentId` (раздел 12) и сверять `Status`, `Amount` и `OrderId` с заказом. `GetState` — единственный вызов, где мы получаем сумму из ответа банка, поэтому именно он источник правды для оплаты.
5. Хост — настройка кассы (`base_url`). DEMO-терминал работает на `securepay.tinkoff.ru/v2` (раздел 1). Стадийность `PayType` согласовывать с настройкой терминала (раздел 20).
6. **TLS:** на сервере должны быть корневой и выпускающий сертификаты Минцифры (раздел 24), иначе запросы к API будут падать с ошибкой проверки сертификата.

## 9. Метод FinishAuthorize («Подтвердить платёж»): нам НЕ нужен

Страница «Подтвердить платёж» в меню банка (`/eacq/api/finish-authorize`) описывает метод **`FinishAuthorize` для мерчантов с собственной платёжной формой**: карточные данные собираются у нас и шифруются публичным ключом банка, для этого нужен сертификат PCI DSS. В нашем сценарии (редирект на форму банка через `Init`) клиент вводит карту на стороне банка, поэтому **этот метод не вызывается**.

⚠ Не путать с **`Confirm` — страница «Подтвердить списание»** (`/eacq/api/confirm`). Именно `Confirm` списывает деньги после `AUTHORIZED` при двухстадийной оплате (`Amount` в копейках, необязательный; `Receipt` обязателен при подключённой онлайн-кассе). Подробности в разделе 10; про 3DS на своей форме — раздел 11.

Что полезно знать из страницы (на случай перехода на свою форму):

- `POST https://securepay.tinkoff.ru/v2/FinishAuthorize`. Есть вкладка «test», сам тестовый адрес на странице не указан, предположительно как у `Init` (`rest-api-test.tinkoff.ru`), проверить.
- Запрос: `TerminalKey` (≤64), `PaymentId` (≤20), `Token`, `CardData` (строка `PAN=…;ExpDate=MMYY;CardHolder=…;CVV=…`, шифруется открытым ключом **X509 RSA 2048**, затем Base64; ключ выдаётся при регистрации терминала, лежит в ЛК → «Магазины»), `IP` (**обязателен для 3DS v2**; IPv6 в полном виде, 8 групп по 4 символа), `SendEmail` + `InfoEmail`, `Source` и `Route` (`ACQ`, `MC`, `EINV`, `WM`; `Route` обязателен для Apple Pay/Google Pay), `EncryptedPaymentData` (только Apple Pay/Google Pay), `Amount`, `DATA` (параметры браузера для 3DS: `threeDSCompInd`, `language`, `timezone`, `screen_height`, `screen_width`, `cresCallbackUrl`, `colorDepth`, `javaEnabled`).
- **Ловушка:** `deviceChannel` по умолчанию `02` (браузер) и подставляется сам. Если передать `deviceChannel=02` явно, запрос завершится ошибкой `ErrorCode=204`, `Message=Неверные параметры`, `Details=Неверный токен. Проверьте пару TerminalKey/SecretKey`.
- Статусы в ответе: `CONFIRMED` (одностадийная), `AUTHORIZED` (двухстадийная), `3DS_CHECKING` (нужна проверка 3DS), `REJECTED`. Если на своей форме платёж завис в `3DS_CHECKING`, обращаться к эмитенту.
- Варианты ответа 200: `Without3DS`; `With3DS` (добавляются `MD`, `PaReq`, `ACSUrl` — отправить запрос на ACS и перенаправить туда клиента); `WithThreeDSv2APP` (для приложения: `TdsServerTransId`, `AcsTransId`, `AcsInterface`, `AcsUiTemplate`, `AcsSignedContent`, `AcsReferenceNumber`, `SdkTransID`); `WithThreeDSv2BRW` (для браузера: `TdsServerTransId`, `AcsTransId`, `ACSUrl`); `ErrorResponse`. Во всех успешных есть необязательные `RebillId` и `CardId`.
- Ответ 500 как у `Init`: `ErrorCode: "9999"`, `Message`, `Causes`.
- Примеры в документации содержат заглушки: ответ с `Success: true`, `Status: "NEW"` и `Message: "Неверные параметры"` одновременно — это шаблон, на него не ориентироваться.

## 10. Метод Confirm («Подтвердить списание»)

`POST https://securepay.tinkoff.ru/v2/Confirm` (тест: `POST https://rest-api-test.tinkoff.ru/v2/Confirm`).

Подтверждает списание денег. Используется **только при двухстадийном платеже** (`PayType=T`) и применим **только к платежам в статусе `AUTHORIZED`**. Сумма списания **может быть меньше или равна** сумме авторизации. При одностадийной оплате (`PayType=O`) метод не нужен.

### Запрос

| Параметр | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | ≤ 64 |
| `PaymentId` | да | ≤ 20, идентификатор платежа из ответа `Init` |
| `Token` | да | Подпись (раздел 3) |
| `IP` | нет | IP-адрес покупателя |
| `Amount` | нет | Сумма списания в копейках. **Если не передан, берётся `Amount` из `Init`** |
| `Receipt` | условно | Чек, **обязателен, если подключена онлайн-касса** |
| `Shops` | для маркетплейсов | Не наш случай |
| `Route` | нет | Способ платежа: `TCB`, `BNPL` (рассрочка), нам не нужен |
| `Source` | нет | Источник: `installment`, `BNPL`, нам не нужен |

В `Token` входят только скалярные поля корня: `TerminalKey`, `PaymentId`, `IP`, `Amount`, `Route`, `Source`. `Receipt` и `Shops` в подпись **не входят**.

Дополнительные поля `Receipt`, которых не было в `Init` (нужны в основном для маркируемых товаров и агентов, нам обычно не нужны): `ClientInfo {Birthdate, Citizenship, DocumentCode, DocumentData, Address}`, `Customer`, `CustomerInn`; в позиции `UserData`, `Excise`, `CountryCode`, `DeclarationNumber`, `MeasurementUnit`, `MarkProcessingMode`, `MarkCode {MarkCodeType, Value}`, `MarkQuantity {Numerator, Denominator}`, `SectoralItemProps`; на уровне чека `OperatingCheckProps`, `SectoralCheckProps`, `AddUserProp`, `AdditionalCheckProps`. Для услуги достаточно того же минимального чека, что в `Init` (раздел 6).

⚠ Пример запроса в доке несогласован: `Amount: 19200`, позиция на `10000`, `Payments` на `109200`. В реальном запросе `Amount` = Σ `Items[].Amount`.

### Ответ (HTTP 200)

`ConfirmResponse`:

| Поле | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | |
| `OrderId` | да | ≤ 50 |
| `Success` | да | boolean |
| `Status` | да | Статус транзакции (список ниже) |
| `PaymentId` | да | |
| `ErrorCode` | да | `"0"` — без ошибки |
| `Message` | да | Краткое описание (в примере успеха `"OK"`) |
| `Details` | нет | Подробности (в примере строка `"None"`) |
| `Params` | нет | Массив `{Key, Value}`; в примере `[{"Key": "Route", "Value": "ACQ"}]`, для рассрочки там детали |

**В ответе `Confirm` нет поля `Amount`.** Не ожидать его.

Пример успеха:
```json
{"TerminalKey": "TBankTest", "OrderId": "21057", "Success": true, "Status": "CONFIRMED",
 "PaymentId": "2304882", "ErrorCode": "0", "Message": "OK", "Details": "None",
 "Params": [{"Key": "Route", "Value": "ACQ"}]}
```

Отказ приходит как `ErrorResponse` (`Success`, `ErrorCode`, `Message`, `Details`) с HTTP 200. Внутренняя ошибка — HTTP 500 с `Success`, `ErrorCode`, `Message`, `Causes`, `StackTrace` (пример: `ErrorCode: "9999"`, «Внутренняя ошибка системы.»).

### Полный список статусов транзакции (схема Confirm)

`NEW`, `AUTHORIZING`, `AUTHORIZED`, `AUTH_FAIL`, `CANCELED`, `CHECKING`, `CHECKED`, `COMPLETING`, `COMPLETED`, `CONFIRMING`, `CONFIRMED`, `DEADLINE_EXPIRED`, `FORM_SHOWED`, `PARTIAL_REFUNDED`, `PREAUTHORIZING`, `PROCESSING`, `3DS_CHECKING`, `3DS_CHECKED`, `REVERSING`, `REVERSED`, `REFUNDING`, `REFUNDED`, `REJECTED`, `UNKNOWN`.

Смысл: `*ING` — промежуточные состояния («в процессе»), `CONFIRMED` — деньги списаны, `AUTHORIZED` — деньги заблокированы, `DEADLINE_EXPIRED` — срок платежа истёк. Описаний каждого статуса на странице нет.

### Для адаптера

1. Двухстадийная оплата: по уведомлению `AUTHORIZED` проверить заказ и сумму, затем вызвать `Confirm` с тем же `PaymentId` (и `Receipt`, если касса подключена). Выдавать товар **после** `Status: CONFIRMED`, а не после `AUTHORIZED`.
2. Если `Amount` не передавать, спишется вся авторизованная сумма. Передавать явно, когда списываем меньше.
3. `Confirm` применим только к `AUTHORIZED`. Перед вызовом убедиться, что платёж именно в этом статусе (например, через `GetState`), иначе будет отказ.
4. Ответ `CONFIRMING` (промежуточный) возможен по списку статусов: не считать это ошибкой и не повторять списание, дождаться уведомления `CONFIRMED` или проверить `GetState`.
5. Срок холда по способам оплаты на присланных страницах не указан (по фрагменту поиска до 7 дней для карт, раздел 4): запланировать `Confirm` заранее (например, сразу после проверки заказа).
6. Что происходит при повторном `Confirm` и какие коды ошибок возвращаются для платежа не в `AUTHORIZED`, на странице **не описано**. Не рассчитывать на идемпотентность: перед повтором проверять статус.

```python
import httpx

def tbank_confirm(host: str, terminal_key: str, password: str, payment_id: str,
                  amount_kop: int | None = None, receipt: dict | None = None) -> dict:
    body = {"TerminalKey": terminal_key, "PaymentId": payment_id}
    if amount_kop is not None:
        body["Amount"] = amount_kop
    body["Token"] = tbank_token(body, password)      # до добавления Receipt: он в подпись не входит
    if receipt is not None:
        body["Receipt"] = receipt
    r = httpx.post(f"{host}/v2/Confirm", json=body, timeout=30)
    data = r.json()
    if r.status_code >= 500 or not data.get("Success"):
        raise RuntimeError(data.get("Message") or data)
    return data    # ждём Status == "CONFIRMED"
```

## 11. 3DS на своей форме: Check3dsVersion, 3DS Method, ACS, Submit3DSAuthorization(V2) — нам НЕ нужны

Все пять страниц помечены «**Для мерчантов с собственной платёжной формой**». При редиректе на форму банка (наш сценарий) 3DS проходит клиент на странице банка, наш сервер этих методов не вызывает. Фиксирую кратко, чтобы можно было вернуться, если появится своя форма.

### Цепочка для своей формы (по порядку страниц)

1. `Init` → `PaymentId`.
2. **`Check3dsVersion`** (`POST /v2/Check3dsVersion`, тест `rest-api-test.tinkoff.ru/v2/Check3dsVersion`): запрос `PaymentId`, `TerminalKey`, `CardData` (шифрованные данные карты), `Token`. Ответ: `Version` (`1.0.0` или `2.1.0`), `TdsServerTransID` (для 3DS 2.1), `ThreeDSMethodURL` (для 2.1, необязательный), `PaymentSystem` (например `mir`), `Success`, `ErrorCode`, `Message`, `Details`.
3. Если пришёл `ThreeDSMethodURL` — **3DS Method**: форма POST на этот URL (адрес банка-эмитента, не наш API) в **скрытом iframe**, **таймаут 10 секунд**. Тело — `threeDSMethodData` = Base64(JSON `{"threeDSServerTransID": "...", "threeDSMethodNotificationURL": "..."}`). Я расшифровал пример из доки: `threeDSMethodNotificationURL` указывает на `https://rest-api-test.tinkoff.ru/v2/Complete3DSMethodv2`, то есть уведомление о завершении 3DS Method принимает **банк**. Ответ: `threeDSServerTransID` (≤36).
4. **`FinishAuthorize`** (раздел 9). Если в ответе `3DS_CHECKING`:
   - **3DS 1.0:** клиента перенаправляют на `ACSUrl` формой POST с `MD`, `PaReq`, `TermUrl` (наш обработчик). В ответ на `TermUrl` приходят `MD` и `PaRes` (и `FallbackOnTdsV1=true`, если 2.1 невозможен и произошёл откат на 1.0).
   - **3DS 2.1:** на `ACSUrl` отправляется `creq` (Base64 JSON), ответ `cres` (JSON/JWE, Base64) приходит на `cresCallbackUrl` из `DATA` запроса `FinishAuthorize`.
5. Завершение:
   - **3DS 1.0 → `Submit3DSAuthorization`** (`POST /v2/Submit3DSAuthorization`), **`application/x-www-form-urlencoded`**: `MD`, `PaRes` (обязательные), `PaymentId`, `TerminalKey`, `Token`.
   - **3DS 2.1 → `Submit3DSAuthorizationV2`** (`POST /v2/Submit3DSAuthorizationV2`), тоже form-urlencoded: `PaymentId`, `TerminalKey`, `Token`.
   - Ответ обоих: `TerminalKey`, `OrderId`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `Message`, `Details`. Для v1 статус: `CONFIRMED` (одностадийная), `AUTHORIZED` (двухстадийная), `REJECTED`.
   - При одностадийной оплате списывают деньги, при двухстадийной — блокируют сумму (затем `Confirm`, раздел 10).

### Замечания

- Эти методы принимают данные **формой**, а не JSON. Правила подписи для form-urlencoded запросов (входят ли `MD` и `PaRes` в `Token`) на страницах не описаны. Алгоритм `Token` общий (раздел 3), но состав полей для этих двух методов нужно уточнить у банка.
- Во всех ответах 500 одинаковая схема (`ErrorCode: "9999"`, `Causes`).
- Примеры в документации содержат заглушки (`Message: "string"`, `"None"`), на них не ориентироваться.
- Хосты: боевой `securepay.tinkoff.ru/v2/...`, тестовый `rest-api-test.tinkoff.ru/v2/...`.

## 12. GetState («Получить статус платежа»)

`POST https://securepay.tinkoff.ru/v2/GetState` (тест: `POST https://rest-api-test.tinkoff.ru/v2/GetState`).

### Запрос

| Параметр | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | ≤ 64 |
| `PaymentId` | да | ≤ 20, идентификатор из ответа `Init` |
| `Token` | да | Подпись (раздел 3) |
| `IP` | нет | IP-адрес покупателя |
| `GetPhone` | нет | boolean, получить номер телефона |

В `Token` входят `TerminalKey`, `PaymentId`, а также `IP` и `GetPhone`, **если переданы** (булево как `"true"`/`"false"`).

### Ответ (HTTP 200)

| Поле | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | |
| `Amount` | да | int64, **сумма в копейках** |
| `OrderId` | да | ≤ 50 |
| `Success` | да | boolean |
| `Status` | да | ≤ 20, статус платежа (список в разделе 10) |
| `PaymentId` | да | |
| `ErrorCode` | да | `"0"` — без ошибки. Для СБП при успехе возвращается `0`, **ориентироваться на статус платежа** |
| `Message` | нет | Для СБП при успехе — `OK` |
| `Details` | нет | |
| `RebillId` | нет | ID сохранённых реквизитов |
| `Params` | нет | Массив `{Key, Value}`: информация о способе оплаты и деталях рассрочки |

Пример:
```json
{"Success": true, "ErrorCode": "0", "Message": "OK", "TerminalKey": "TBankTest",
 "Status": "AUTHORIZED", "PaymentId": "13660", "OrderId": "21050",
 "Params": [{"Key": "Route", "Value": "ACQ"}, {"Key": "Source", "Value": "cards"}],
 "Amount": 1230}
```
В `Params` бывают `Route` (например `ACQ`), `Source` (например `cards`), для рассрочки `CreditAmount`, `EndCoolingPeriod`, для цифрового рубля `ParticipantWalletId`, `DrPaymentId`, `DrPaymentSettlementDate`. Нам нужны только `Route` и `Source`.

Отказ — `ErrorResponse` (`Success: false`, `ErrorCode`, `Message`, `Details`) с HTTP 200; внутренняя ошибка — HTTP 500 с `Causes` (раздел 2).

### Как использовать

1. **После вебхука:** вызвать `GetState`, проверить `Success == true`, `OrderId`, `Amount` (копейки, равна сумме заказа) и `Status`. Оплатой считать `CONFIRMED` (одностадийная) либо `CONFIRMED` после `Confirm` (двухстадийная).
2. **Если вебхук не пришёл:** опрашивать `GetState` по `PaymentId` с растущим интервалом, пока статус не станет финальным (`CONFIRMED`, `REJECTED`, `REVERSED`, `REFUNDED`, `DEADLINE_EXPIRED`).
3. Статус `REJECTED`, `DEADLINE_EXPIRED` — платёж не оплачен, клиенту предложить новый платёж (новый `OrderId`).
4. `PaymentURL` в ответе нет.

```python
import httpx

def tbank_get_state(host: str, terminal_key: str, password: str, payment_id: str) -> dict:
    body = {"TerminalKey": terminal_key, "PaymentId": payment_id}
    body["Token"] = tbank_token(body, password)
    r = httpx.post(f"{host}/v2/GetState", json=body, timeout=30)
    data = r.json()
    if r.status_code >= 500 or not data.get("Success"):
        raise RuntimeError(data.get("Message") or data)
    return data    # проверить Status, Amount (копейки), OrderId
```

⚠ Пример `Token` в запросе `GetState` в документации совпадает с примером в `Init` (`7241ac83…`), примеры токенов — заглушки, проверять их нельзя.

## 13. CheckOrder («Получить статус заказа»)

`POST https://securepay.tinkoff.ru/v2/CheckOrder` (тест: `POST https://rest-api-test.tinkoff.ru/v2/CheckOrder`).

Возвращает статус **заказа** по `OrderId` вместе со списком **всех платежей по этому заказу**.

### Запрос

`TerminalKey` (≤ 64), `OrderId` (≤ 50), `Token`. В подпись входят эти три поля.

### Ответ (HTTP 200)

Верхний уровень: `TerminalKey`, `OrderId`, `Success`, `ErrorCode`, `Message` (≤ 255), `Details`, **`Payments`** (массив).

Элемент `Payments[]`:

| Поле | Описание |
|---|---|
| `PaymentId` | ID платежа в Т-Бизнес |
| `Amount` | int64, сумма операции в копейках |
| `Status` | статус операции |
| `RRN` | уникальный идентификатор операции |
| `Success` | успешность |
| `ErrorCode`, `Message` | код и описание ошибки |
| `SbpPaymentId`, `SbpCustomerId` | для СБП: ID платежа в СБП, хэш телефона покупателя |
| `DrPaymentId`, `DrPaymentSettlementDate`, `ParticipantWalletId` | для цифрового рубля |

Пример:
```json
{"TerminalKey": "TBankTest", "OrderId": "21057", "Success": true, "ErrorCode": "0",
 "Message": "OK", "Details": "None",
 "Payments": [{"PaymentId": "124671934", "Amount": 13660, "Status": "NEW",
               "RRN": "12345678", "Success": true, "ErrorCode": 0, "Message": "None"}]}
```

⚠ Несоответствие схемы и примера: в схеме `Payments[].Success` и `ErrorCode` — **строки**, а в примере `Success: true` (булево) и `ErrorCode: 0` (число). Разбирать терпимо: приводить к строке и сравнивать с `"0"`/`"true"`.

### Как использовать

1. **После сбоя или таймаута `Init`:** вызвать `CheckOrder` по `OrderId`.
   - `Payments` пустой → платёж не создан, `Init` можно повторить с тем же `OrderId`.
   - Есть платёж со статусом `NEW` → платёж создан, но **ссылку (`PaymentURL`) получить нельзя**. Создавать новый платёж с новым `OrderId`.
   - Есть платёж `CONFIRMED` → заказ оплачен, повторно не создавать.
2. Массив `Payments` позволяет найти среди попыток оплаты одного заказа успешную.
3. Для проверки суммы после вебхука основным остаётся `GetState` по `PaymentId`, `CheckOrder` годится как запасной вариант.

```python
def tbank_check_order(host: str, terminal_key: str, password: str, order_id: str) -> dict:
    body = {"TerminalKey": terminal_key, "OrderId": order_id}
    body["Token"] = tbank_token(body, password)
    r = httpx.post(f"{host}/v2/CheckOrder", json=body, timeout=30)
    data = r.json()
    if r.status_code >= 500 or not data.get("Success"):
        raise RuntimeError(data.get("Message") or data)
    return data    # data["Payments"] — все платежи по заказу
```

## 14. Cancel («Отменить платёж»)

`POST https://securepay.tinkoff.ru/v2/Cancel` (на странице есть вкладка «test», тестовый адрес по аналогии с остальными: `rest-api-test.tinkoff.ru/v2/Cancel`).

Отменяет платёж: отмена холда, частичная отмена, возврат оплаченного. Какой статус получится — в таблице раздела 23 (сценарий «Отмена и возврат платежа»).

### Запрос

| Параметр | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | ≤ 64 |
| `PaymentId` | да | Идентификатор платежа |
| `Token` | да | Подпись |
| `IP` | нет | IP-адрес покупателя |
| `Amount` | нет | Сумма в копейках. **Если не передан, берётся `Amount` из `Init`.** Для платежа в статусе **`NEW` поле игнорируется**, отмена всегда на полную сумму |
| `Receipt` | условно | Чек. **Обязателен при частичной отмене, если подключена онлайн-касса.** При полной отмене чек не передаётся. При частичной передаются **только отменяемые товары**; данные могут отличаться от переданных в `Init` |
| `Shops` | для маркетплейсов | Не наш случай |
| `QrMemberId` | нет | Код банка в классификации СБП, в который делать возврат (для возврата по СБП) |
| `Route` | нет | `TCB`, `BNPL`, нам не нужен |
| `Source` | нет | `installment`, `BNPL`, нам не нужен |
| `ExternalRequestId` | нет* | ≤ 255. **Ключ идемпотентности и ID операции на нашей стороне** (см. ниже) |

В `Token` входят скалярные поля корня: `TerminalKey`, `PaymentId`, `IP`, `Amount`, `QrMemberId`, `Route`, `Source`, `ExternalRequestId` (если переданы). `Receipt` и `Shops` не входят.

### ExternalRequestId — идемпотентность возвратов

- Если поле **не передано или пустое**, запрос обрабатывается **без проверки ранее созданных возвратов**. То есть при повторе (таймаут, 500, дубль вебхука) **можно вернуть деньги дважды**.
- Если заполнено: перед возвратом банк проверяет, есть ли отмена с таким `ExternalRequestId`. Есть — в ответе вернётся **текущее состояние операции**, нет — платёж будет отменён.
- ⚠ В справочнике ошибок есть код **3025** «Отмена с данным `ExternalRequestId` уже была выполнена», то есть на повтор возможна и ошибка, а не только «текущее состояние». Обрабатывать оба варианта: при ошибке 3025 проверить `GetState`.
- Обязателен для операций «Долями» (значение в формате UUID v4) и в рассрочку (строка до 100 символов). Для AlfaPay длина не более 30 символов.

⚠ Для адаптера: **всегда передавать `ExternalRequestId`** (UUID v4 без дефисов или с ними, до 30 символов безопаснее: `uuid4().hex[:30]`), хранить его в записи о возврате и при повторе использовать тот же.

### Ответ (HTTP 200)

| Поле | Обяз. | Описание |
|---|---|---|
| `TerminalKey`, `OrderId`, `PaymentId` | да | |
| `Success` | да | boolean |
| `Status` | да | Статус транзакции после отмены |
| `OriginalAmount` | да | int64, **сумма в копейках до отмены** |
| `NewAmount` | да | int64, **сумма в копейках после отмены** |
| `ErrorCode` | да | `"0"` — без ошибки |
| `Message` | нет | ≤ 255 |
| `Details` | нет | |
| `ExternalRequestId` | нет | Возвращается наш ID операции |

Пример:
```json
{"TerminalKey": "TBankTest", "OrderId": "21057", "Success": true, "Status": "REVERSED",
 "OriginalAmount": 13000, "NewAmount": 5000, "PaymentId": "2304882",
 "ErrorCode": "0", "Message": "OK", "Details": "None",
 "ExternalRequestId": "756478567845678436"}
```
Отказ — `ErrorResponse` с HTTP 200, внутренняя ошибка — HTTP 500 (`ErrorCode: "9999"`, `Causes`).

⚠ В примере статус `REVERSED` при `NewAmount` 5000 (частичная отмена) выглядит странно: по сценарию «Отмена и возврат» частичная отмена холда даёт `PARTIAL_REVERSED`, а частичный возврат — `PARTIAL_REFUNDED`. Не ориентироваться на этот пример при написании кода: проверять `NewAmount` и `OriginalAmount`, а затем подтверждать `GetState`.

### Для адаптера

1. Отмена холда (`AUTHORIZED`) и возврат оплаченного (`CONFIRMED`) — один метод `Cancel`.
2. Полный возврат: без `Amount` и без `Receipt`. Частичный: `Amount` (копейки) + `Receipt` с **возвращаемыми** позициями, если касса подключена.
3. Результат сверять: `NewAmount == OriginalAmount - возвращённая сумма`.
4. Уведомления об изменении статуса после отмены приходят на `NotificationURL`, обрабатывать идемпотентно.

```python
def tbank_cancel(host, terminal_key, password, payment_id,
                 amount_kop=None, receipt=None, external_request_id=None):
    body = {"TerminalKey": terminal_key, "PaymentId": payment_id}
    if amount_kop is not None:
        body["Amount"] = amount_kop
    if external_request_id:
        body["ExternalRequestId"] = external_request_id
    body["Token"] = tbank_token(body, password)
    if receipt is not None:          # только при частичной отмене и подключённой кассе
        body["Receipt"] = receipt
    r = httpx.post(f"{host}/v2/Cancel", json=body, timeout=30)
    data = r.json()
    if r.status_code >= 500 or not data.get("Success"):
        raise RuntimeError(data.get("Message") or data)
    return data     # OriginalAmount, NewAmount, Status
```

## 15. Charge («Провести платёж по сохранённым реквизитам»)

`POST https://securepay.tinkoff.ru/v2/Charge` (тест: `rest-api-test.tinkoff.ru/v2/Charge`, по аналогии с остальными).

Проводит **COF-операцию**: безакцептное списание по ранее сохранённым реквизитам и `RebillId`. **Это основа подписок.**

### Важно: Charge не создаёт платёж, а завершает уже созданный

В запросе **обязателен `PaymentId`**. Значит, порядок такой:
1. `Init` для **нового платежа** (новый `OrderId`, `Amount`, при необходимости `Receipt`, `PayType`, `DATA.OperationInitiatorType`) → получаем `PaymentId`.
2. `Charge` с этим `PaymentId` и `RebillId`.

**В `Charge` нет ни `Amount`, ни `Receipt`**: сумма и чек берутся из `Init`. Поэтому чек для каждого периода нужно передавать в `Init`, а не в `Charge`.

### Запрос

| Параметр | Обяз. | Описание |
|---|---|---|
| `TerminalKey` | да | ≤ 64 |
| `PaymentId` | да | ≤ 20, платёж из `Init` |
| `RebillId` | да | ID сохранённых реквизитов. Приходит **в уведомлении после успешной родительской CC-операции** (платёж с `Recurrent=Y`) |
| `Token` | да | Подпись |
| `IP` | нет | IP покупателя |
| `SendEmail` | нет | boolean, отправлять уведомление об оплате на почту |
| `InfoEmail` | условно | Email, обязателен при `SendEmail=true` |

В `Token`: `TerminalKey`, `PaymentId`, `RebillId`, а также `IP`, `SendEmail` (булево как `"true"`), `InfoEmail`, если переданы.

### Ответ (HTTP 200)

`TerminalKey`, `Amount` (копейки), `OrderId`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `Message`, `Details`.

**`Status`: `CONFIRMED` — платёж выполнен, `REJECTED` — не выполнен.**

```json
{"TerminalKey": "TBankTest", "Amount": 100000, "OrderId": "21050", "Success": true,
 "Status": "CONFIRMED", "PaymentId": "13660", "ErrorCode": "0"}
```
Отказ — `ErrorResponse`, внутренняя ошибка — HTTP 500.

⚠ Токен в примере `Charge` совпадает с токеном в примере `FinishAuthorize` (`f5a3be47…`): примеры токенов — заглушки.

### Для адаптера

0. Ошибка **10** («Метод Charge заблокирован для данного терминала») означает, что платежи по сохранённым реквизитам не включены на терминале (раздел 7).
1. Статус `CONFIRMED` из ответа — оплата списана. `REJECTED` — списание не прошло: считать неудачей периода (раздел 19).
2. После `Charge` по-прежнему приходит вебхук. Обрабатывать идемпотентно, чтобы не продлить подписку дважды (ответ `Charge` и вебхук про один и тот же `PaymentId`).
3. Повтор `Charge` при сбое (500, таймаут): **сначала `GetState` по `PaymentId`**. Идемпотентность `Charge` на странице не описана, повторять вслепую нельзя.
4. Стадийность COF по умолчанию берётся из `PayType` в `Init` или настроек терминала. Для периодических списаний ставить `PayType=O` (одностадийная): тогда результат — сразу `CONFIRMED` и `Confirm` не нужен. Этот совет мой вывод: на странице `Charge` упомянуты только `CONFIRMED` и `REJECTED`.

```python
def tbank_charge(host, terminal_key, password, payment_id, rebill_id):
    body = {"TerminalKey": terminal_key, "PaymentId": payment_id, "RebillId": rebill_id}
    body["Token"] = tbank_token(body, password)
    r = httpx.post(f"{host}/v2/Charge", json=body, timeout=60)
    data = r.json()
    if r.status_code >= 500:
        raise RuntimeError("charge: result unknown, check GetState")   # не повторять вслепую
    return data     # Success и Status: CONFIRMED или REJECTED
```

## 17. Покупатели и карты: AddCustomer, GetCustomer, RemoveCustomer, AddCard, GetAddCardState, GetCardList, RemoveCard

Все методы — `POST https://securepay.tinkoff.ru/v2/<Метод>` (тест: `rest-api-test.tinkoff.ru/v2/...`), в `Token` входят скалярные поля корня (булево как `"true"`/`"false"`).

⚠ **Длина `CustomerKey`:** в запросах указано «≤ 255», а в ответах и в `AddCard`/`RemoveCard` — «≤ **36**». Использовать `CustomerKey` не длиннее 36 символов (например UUID), иначе возможны ошибки.

### Покупатели

| Метод | Назначение | Запрос | Ответ |
|---|---|---|---|
| **`AddCustomer`** | Регистрирует покупателя в связке с терминалом | `TerminalKey`, `CustomerKey` (обяз.), `Token`, `IP`, `Email` (≤100), `Phone` (≤15, формат `+{цифры}`) | `TerminalKey`, `CustomerKey`, `ErrorCode`, `Success`, `Message`, `Details` |
| **`GetCustomer`** | Возвращает сохранённые данные | `TerminalKey`, `CustomerKey`, `Token`, `IP` | то же + `Email` (≤64), `Phone` (≤64) |
| **`RemoveCustomer`** | Удаляет сохранённые данные покупателя | `TerminalKey`, `CustomerKey`, `Token`, `IP` | `TerminalKey`, `CustomerKey`, `ErrorCode`, `Success`, `Message`, `Details` |

- Обязательна ли регистрация покупателя перед привязкой карты или платежом с `Recurrent=Y`, **на страницах не сказано**. В примерах `AddCard` и `Init` `CustomerKey` передаётся без предварительного `AddCustomer`. Проверить на DEMO-терминале.
- Что именно удаляет `RemoveCustomer` (только контакты или и карты), не описано. Для отвязки карты использовать `RemoveCard`, а не `RemoveCustomer`.
- Примеры в документации с заглушками (`Message: "Неверные параметры"` при `Success: true`) — не ориентироваться.

### AddCard: привязка карты без платежа

Запрос: `TerminalKey`, `CustomerKey`, `Token` (обяз.), `CheckType`, `IP`, `ResidentState`.

**`CheckType`** (по умолчанию `NO`):

| Значение | Что делает | `RebillId` |
|---|---|---|
| `NO` | Сохраняет карту без проверок | **Не возвращается**, для рекуррента не годится |
| `HOLD` | Списание-проверка на 0 руб. | Возвращается для терминалов без поддержки 3DS |
| `3DS` | Проверка 3DS и списание на 0 руб. | Только для карт с поддержкой 3DS; карты без 3DS **не привяжутся** |
| `3DSHOLD` | Проверка, поддерживает ли карта 3DS; если нет — списание на 0 руб. | Возвращается по результату проверки |

`ResidentState`: `true` — карта РФ, `false` — не РФ, `null` — универсальная. Булево/`null` в подписи неоднозначны, поэтому параметр лучше **не передавать**, если не нужен.

Ответ: `PaymentId`, `TerminalKey`, `CustomerKey`, **`RequestKey`** (ID запроса привязки), `ErrorCode`, `Success`, **`PaymentURL`** (ссылка на форму привязки карты банка), `Message`, `Details`. Клиента отправить на `PaymentURL`.

### GetAddCardState: статус привязки

Запрос: `TerminalKey`, `RequestKey`, `Token`. Ответ: `TerminalKey`, `RequestKey`, `Status`, `Success`, `CardId` (≤40), `RebillId`, `ErrorCode`, `Message`, `Details`, `CustomerKey`.

Статусы: `NEW` (сессия создана), `FORM_SHOWED` (форма показана), `3DS_CHECKING`, `3DS_CHECKED`, `AUTHORIZING` (платёж на 0 руб.), `AUTHORIZED` (0 руб. прошёл), **`COMPLETED`** (карта привязана), **`REJECTED`** (привязать не удалось).

Банк присылает и **уведомление о привязке карты** на `NotificationURL` (в его подписи участвуют `TerminalKey`, `CustomerKey`, `RequestKey`, `Success`, `Status`, `PaymentId`, `ErrorCode`, `CardId` и другие, полный список не получен).

### GetCardList: список карт покупателя

Запрос: `TerminalKey`, `CustomerKey`, `Token` (обяз.), `SavedCard` (boolean, «карта сохранена для оплаты в один клик»), `IP`.

Возвращает **все карты покупателя, привязанные к терминалу, включая удалённые**. Поля карты: `CardId`, `Pan` (маска), **`Status`** (`A` — активная, `D` — удалённая), `RebillId`, `CardType` (0 — карта списания, 1 — пополнения, 2 — обе), `ExpDate` (`MMYY`).

⚠ Пример ответа в доке — один объект (с опечаткой `RebillId'`), а метод возвращает список. Разбирать терпимо: и массив, и одиночный объект. Брать только `Status == "A"`.

### RemoveCard: удалить карту

Запрос: `TerminalKey`, `CustomerKey` (≤36), `CardId` (≤40), `Token`, `IP`. Ответ: `TerminalKey`, `Status` (**`D` — удалена**), `CustomerKey`, `CardId`, `CardType`, `Success`, `ErrorCode`, `Message`, `Details`. Удаляет по **`CardId`**, а не по `RebillId`.

⚠ Прекращает ли удаление карты действие `RebillId`, на странице не написано. Логично, что да, но проверить на DEMO: после `RemoveCard` попытка `Charge` со старым `RebillId` должна завершиться ошибкой.

### AttachCard: нам не нужен

«Привязать карту» для мерчантов с **собственной формой**: `TerminalKey`, `RequestKey`, `CardData` (шифрованные данные), `deviceChannel`, `DATA` (для 3DS 2.1 — параметры `ThreeDSv2` и заголовки `User-Agent`, `Accept`), `Token`. Ответ содержит `CardId`, `RebillId`, `Status` и при 3DS — `ACSUrl`, `MD`, `PaReq`. Нужен только при своей форме и PCI DSS.

```python
def tbank_post(host, terminal_key, password, method, **fields):
    body = {"TerminalKey": terminal_key, **fields}
    body["Token"] = tbank_token(body, password)
    r = httpx.post(f"{host}/v2/{method}", json=body, timeout=30)
    data = r.json()
    if r.status_code >= 500:
        raise RuntimeError(data)
    return data

# привязка без платежа: ссылку на форму отдаём клиенту
res = tbank_post(host, tk, pw, "AddCard", CustomerKey=customer_uuid, CheckType="3DSHOLD")
payment_url, request_key = res["PaymentURL"], res["RequestKey"]

state = tbank_post(host, tk, pw, "GetAddCardState", RequestKey=request_key)
# state["Status"] == "COMPLETED" -> сохранить CardId и RebillId

cards = tbank_post(host, tk, pw, "GetCardList", CustomerKey=customer_uuid)
tbank_post(host, tk, pw, "RemoveCard", CustomerKey=customer_uuid, CardId=card_id)
```
(`GetCardList` может вернуть список, а не словарь; обрабатывать оба случая.)

## 18. Методы и разделы меню, которые нам не нужны (или нужны не сейчас)

- **`getConfirmOperation`** («Справка по операции»): `POST /v2/getConfirmOperation`, формирует справку об операции (только карта, T-Pay, СБП, Mir Pay) и отправляет на наш `CallbackUrl` (его нужно заранее добавить в белый список банка через чат ЛК) или на email (до трёх адресов). `PaymentIdList` — массив **чисел**. **`Token` считается только из `Password` и `TerminalKey`.** Для приёма оплаты не нужен.
- **`SendClosingReceipt`** («Отправить закрывающий чек в кассу»): `POST https://securepay.tinkoff.ru/cashbox/SendClosingReceipt` (путь **`/cashbox/`**, не `/v2/`; указан только боевой адрес). Запрос: `TerminalKey`, `PaymentId`, `Receipt`, `Token`. Ответ: `Success`, `ErrorCode`, `Message`. Нужен, **только если принимали предоплату** (`PaymentMethod` `full_prepayment`, `prepayment`, `advance`) и при передаче услуги нужно пробить закрывающий чек. Если везде `PaymentMethod=full_payment`, не нужен.

⚠ **Согласовать с нашим кодом:** в `payments_remaining.py` общая модель чека по умолчанию ставит `PayMethod.FULL_PREPAYMENT`. Для Т-Банка при разовой оплате услуги, которая оказывается сразу (запуск бота), использовать **`full_payment`**, иначе без закрывающего чека (`SendClosingReceipt`) возникнет налоговая недоработка. Для подписок «оплата вперёд за период» вопрос признака расчёта решает бухгалтер продавца.

### Раздел меню «Другие способы приема платежей»

СБП (8 страниц), T-Pay (2), SberPay (2), Mir Pay (1), Alfa Pay (1), цифровой рубль (2). При **редиректе на форму банка** эти способы включаются на форме автоматически (страница «Платёжная форма банка»), отдельно вызывать их методы не нужно. Присылать их не надо. Исключение: если захотите подписки через **СБП**, тогда понадобится страница привязки счёта СБП (среди страниц раздела СБП) и метод `ChargeQr` (раздел 16).

## 19. Подписки через Т-Банк: сквозной сценарий

У банка **нет объекта «подписка»**. Расписание ведём мы, банк хранит реквизиты (`RebillId`) и проводит списания. Типы операций и значения `OperationInitiatorType` подтверждены страницей «Платежи по сохранённым реквизитам» (раздел 7).

### Способ сохранить карту (родительская операция)

| | A. CC-покупка: первый платёж | B. CC-привязка: `AddCard` |
|---|---|---|
| Когда | Клиент сразу платит за первый период | Замена карты, привязка до оплаты |
| `Init` / вызов | `Init`: `Recurrent=Y`, `CustomerKey`, `DATA.OperationInitiatorType="1"` | `AddCard` (`CheckType` не `NO`), клиенту `PaymentURL` |
| Где берём `RebillId` | в уведомлении после авторизации | в уведомлении о привязке или `GetAddCardState` (`COMPLETED`) |

⚠ **Карты, сохранённые покупателем при обычной оплате (в один клик, без `Recurrent=Y`), использовать для рекуррентных платежей нельзя** (FAQ). Рекуррентные списания возможны только по карте, привязанной как родительская CC-операция (путь A или B). Первый платёж всегда проходит с 3DS. Оплата в один клик требует 3DS при каждом платеже.

Для подписки основной путь A. Путь B нужен, чтобы клиент **заменил карту** после неудачного списания, не платя повторно. Для `Delayed-Charge` и `No-Show` привязка в роли родительской не подходит, для `Recurring` (`R`) страница ограничений не называет.

### Подготовка

- **Платежи по сохранённым реквизитам включены на терминале** (по умолчанию выключены): DEMO — acq_help@tbank.ru, боевой — персональный менеджер. Иначе `Charge` вернёт ошибку **10**.
- ECOM-терминал.
- **Дополнительное согласие клиента (акцепт)** на автосписания обязательно (FAQ). Текст согласия нужно показать клиенту до первого платежа, а в интерфейсе дать способ отказаться. Включает автоплатежи персональный менеджер.

### Первый платёж (CC-покупка)

`Init` с `Amount`, `OrderId`, **`Recurrent=Y`**, **`CustomerKey`** (UUID ≤ 36), **`DATA {"OperationInitiatorType": "1"}`**, `Receipt`, `NotificationURL`. Без `CustomerKey` банк вернёт внутреннюю ошибку (тест-кейс №6). Для аутентификации картой обязателен 3DS или CVV. После оплаты в уведомлении придут **`RebillId`**, `CardId`, `CustomerKey`. Сохранить их у подписки (зашифрованно). Проверить через `GetCardList` (`Status == "A"`).

### Каждый следующий период (MIT COF Recurring)

1. Уникальный детерминированный `OrderId`, например `sub<id>p<номер периода>`.
2. **`CheckOrder`** по нему: есть `CONFIRMED` — ничего не создавать; есть `NEW` — создать новый платёж с новым `OrderId` (`...r2`).
3. **`Init`**: `Amount`, `Receipt`, **`DATA {"OperationInitiatorType": "R"}`**, `NotificationURL`. Без перенаправления на `PaymentURL`.
4. **`Charge`** (`PaymentId`, `RebillId`, раздел 15).
5. `CONFIRMED` — продлить на период, сохранить `PaymentId`; `REJECTED` — неудача.
6. Вебхук по тому же `PaymentId` обработать идемпотентно: при одностадийной оплате придут `AUTHORIZED` и `CONFIRMED`.
7. При сбое `Charge` (500, таймаут): `GetState` по `PaymentId`, повторять вслепую нельзя.

Стадийность COF: `PayType` в `Init` или настройка терминала (через acq_help@tbank.ru). Для периодических списаний нужна **одностадийная**, чтобы результат был сразу `CONFIRMED`.

### Что делать при отказе

| Код ошибки | Что значит | Действие |
|---|---|---|
| 1051, 103, 116 | Недостаточно средств | Мягкий отказ: повторить через сутки-двое (3 попытки), клиенту «пополните карту» |
| 1033, 1054, 252 | Срок карты истёк | Жёсткий отказ: просить новую карту (`AddCard`) |
| 1057, 1058 | Клиент запретил такие операции | Жёсткий: новая карта |
| 1041, 506, 600 | Карта утеряна / в чёрном списке | Жёсткий: новая карта |
| 262 | Истёк срок родительского платежа | Жёсткий: заново сохранить карту |
| 107 | Неверный `CardId` | Карты нет, новая привязка |
| 104 | Ошибка выполнения рекуррента | Повторить позже, затем жёсткий |
| 10 | `Charge` заблокирован на терминале | Настройка, не повторять |
| 1125, 1126 | Неверный `OperationInitiatorType` / несогласованность с `RebillId` | Ошибка кода |
| 20 | Повтор `OrderId` | Новый `OrderId` |

После исчерпания попыток подписку останавливаем (доступ до конца оплаченного периода). Клиенту отправляем ссылку `AddCard`, после успешной привязки сохраняем новые `CardId` и `RebillId`, затем `RemoveCard` по старому `CardId`.

### Отмена подписки клиентом

1. Остановить расписание.
2. **`RemoveCard` по `CardId`** (раздел 17).
3. Пометить `RebillId` у себя недействительным.
4. `RemoveCustomer` не вызывать, если клиент может вернуться: что он удаляет, не описано.

### Возврат

`Cancel` по `PaymentId` нужного периода с `ExternalRequestId` (раздел 14).

### Что хранить

`CustomerKey`, `RebillId`, `CardId`, расписание (следующая дата, номер периода), число неудач, `OrderId` и `PaymentId` каждого списания, `RequestKey` активной привязки.

### Проверить на DEMO-терминале до запуска

1. Что платежи по сохранённым реквизитам включены (иначе ошибка 10).
2. Что `DATA.OperationInitiatorType="1"` в первом платеже и `"R"` в периодических принимаются (иначе 1125/1126). Страница показывает параметр без `DATA`, примеры `Init` и «Своей формы» кладут его в `DATA`.
3. Нужно ли `AddCustomer` перед платежом с `Recurrent=Y`.
4. Что `Charge` после `RemoveCard` по старому `RebillId` отклоняется.
5. Идемпотентность `Charge` и результат повторного вызова.
6. Проходит ли `Receipt` в `Init` каждого периода на вашей кассе.
7. Работает ли `CheckType` вашего выбора для карт «Мир» и карт без 3DS (для «Мир» может потребоваться настройка 3DS 2.0, ошибка 1235).

## 20. Тест-кейсы и DEMO-терминал

Источник: страница «Тест-кейсы» (прохождение необязательно, но удобно как проверка).

**Есть два способа тестирования** (раздел 1): тест-кейсы на DEMO-терминале и боевом хосте, либо тестовые платежи на боевом терминале (без `DEMO`) и тестовом хосте `rest-api-test.tinkoff.ru`. Реальные карты в тесте не работают, тестовые карты работают **только в тестовой среде** (раздел «Тестовые карты», ниже).

- Для тест-кейсов используйте **тестовый терминал с приставкой DEMO**. **Запросы с него отправляются на боевую среду `https://securepay.tinkoff.ru/v2`** (раздел 1).
- Запуск: ЛК интернет-эквайринга → **Магазины** → вкладка **Терминалы** → «Тестовый» → «Тестировать». При выборе тест-кейса показываются данные карты. Провести платежи и нажать «Проверить».
- **Нельзя передавать параметры, противоречащие настройкам терминала.** Пример: на терминале двухстадийная оплата, а в `Init` передан `PayType=O`. Менять стадийность: ЛК → Магазины → **Прием оплаты** → блок «Списываем деньги с покупателя»: «После оплаты заказа» (одностадийная) или «После подтверждения заказа» (двухстадийная).

⚠ Для платформы с чужими терминалами из этого следует: **`PayType` надо согласовывать с настройкой терминала продавца**. Безопаснее всего **не передавать `PayType`**, а обрабатывать оба исхода (`CONFIRMED` сразу или `AUTHORIZED` с последующим `Confirm`). Либо хранить настройку стадийности в кассе продавца и передавать её.

### Тестовые карты (только тестовая среда)

Источник: страница «Тестовые карты». Срок действия — любой (на странице `12/30`), CVV `123`. Все карты платёжной системы «Мир». Привязанные тестовые карты с разными сроками можно посмотреть методом `GetCardList`.

**Оплата с 3DS 2.0**

## 22. Платёжная форма банка: включение и использование (наш сценарий)

Источник: страница «Платёжная форма банка». Это готовый интерфейс со встроенными способами оплаты. Используется при создании ссылки на оплату, редиректе, iframe, мобильном приложении, модулях CMS.

### Как включить (в ЛК продавца)

1. ЛК интернет-эквайринга → **Магазины** → вкладка **Терминалы** → **Настроить** → тип подключения **«Универсальное»**.
2. Вкладка **Приём оплаты** → блок **«Готовая платёжная форма от Т-Банка»** → **Настроить** → включить нужные способы оплаты (карта, СБП, T-Pay и другие).
3. Перед началом приёма платежей банк просит пройти **чек-лист запуска** (страницу чек-листа я не получил).

⚠ Для Bot Factory это шаги продавца (или нашей команды, если терминал платформы). Без «Универсального» типа подключения и включённых способов `PaymentURL` может не вернуться. Тестовая платёжная форма есть по ссылке на странице (адрес в присланном тексте не указан).

### Как использовать

1. Бэкенд вызывает **`Init`** с `TerminalKey`, `Amount`, `OrderId`, `Token`, **`DATA.OperationInitiatorType`** (см. раздел 2) и при онлайн-кассе `Receipt`.
2. Из ответа берёт **`PaymentURL`** и отдаёт покупателю. Редирект предпочтительно JS-кодом; если форма HTML `<form>`, то **`method="GET"`**. В Telegram-боте достаточно отдать ссылку кнопкой.
3. К `PaymentURL` можно добавить `?theme=dark` или `?theme=light` (по умолчанию тема подстраивается под ОС покупателя) и `?language=ru` или `?language=en`.
4. Результат: уведомление на `NotificationURL` (раздел 5) и проверка `GetState`.
5. Отмена и возврат — раздел 23.

⚠ В «Быстром старте» страницы сказано, что статус `CONFIRMED` возвращается в ответе `Init`. Для редиректа это неверно (на ответ `Init` приходит `NEW`): результат оплаты узнаём только из уведомления или `GetState`. Это шаблонная фраза из общего текста.

### Получение данных о платеже (обзор методов)

- `GetState` — данные по конкретному платежу (раздел 12).
- `CheckOrder` — история платежей по заказу и их текущий статус (раздел 13).
- `getConfirmOperation` — справка по операции на email или на URL сервиса (Base64), только карта, T-Pay, СБП, Mir Pay; URL нужно предварительно добавить в белый список через чат ЛК (раздел 18).
- «Получить статус возврата» — только для возвратов по СБП (страница не получена).
- Документы по операциям можно скачать в ЛК интернет-эквайринга, уведомления настраиваются по разным типам операций.

Страница не описывает рекомендованного сочетания вебхуков и опроса, поэтому схема из разделов 5 и 12 (вебхук как триггер, `GetState` как проверка) остаётся нашим решением.

## 23. Отмена и возврат платежа: сценарий

Источник: страница «Отмена и возврат платежа». Используется метод `Cancel` (раздел 14).

| Статус платежа | Что делаем | Результат |
|---|---|---|
| `NEW` (ссылка создана, не оплачена) | `Cancel`, `Amount` игнорируется, всегда полная отмена | `CANCELED` |
| `AUTHORIZED` (холд) | `Cancel`: полная по умолчанию, частичная с `Amount` | `REVERSED` (полная) или `PARTIAL_REVERSED` (частичная). Холд на счёте покупателя снимается |
| `CONFIRMED` (списано) | `Cancel`: полный возврат по умолчанию, частичный с `Amount` | `REFUNDED` (полный) или `PARTIAL_REFUNDED` (частичный). Деньги возвращаются на счёт, с которого платил покупатель |

- В «Быстром старте» формы написано, что платёж можно отменить «в любом статусе». Практически это три сценария таблицы.
- **Возврат и отмену можно делать и вручную в ЛК** интернет-эквайринга без комиссии: раздел **Операции** → «Отменить» (для отмены) или «Вернуть» (для возврата).
- **Чарджбэк:** если покупатель оспаривает платёж у своего банка, это происходит помимо нас (см. также ошибку 100, причина «клиент опротестовал платёж»).

### Возвраты при онлайн-кассе

- **Частичный возврат:** `Cancel` + объект `Receipt` с позициями, по которым возвращаем деньги, для каждой `Amount`.
- **Полный возврат:** `Cancel` **без** `Receipt`, чек возврата Т-Банк формирует сам.

### Особенности способов оплаты

- **СБП:** возврат можно сделать в другой банк, для этого в `QrMemberId` указывается код банка в классификации СБП.
- **«Рассрочка от Т-Банка»:** отменить можно только в `AUTHORIZED`.
- **«Долями»:** частичная и полная отмена только в `CONFIRMED` или `PARTIAL_REFUNDED`.

### Для адаптера

1. По статусу платежа выбирать действие: `NEW` — отмена ссылки, `AUTHORIZED` — снять холд, `CONFIRMED` — возврат.
2. После вызова проверять итог по уведомлению и `GetState`: `REVERSED`/`PARTIAL_REVERSED`/`REFUNDED`/`PARTIAL_REFUNDED`/`CANCELED`.
3. Для частичных возвратов с кассой передавать `Receipt` с возвращаемыми позициями, для полных — нет.
4. Использовать `ExternalRequestId` (раздел 14) для защиты от двойного возврата.
5. Дать продавцу подсказку: возврат можно сделать и руками в ЛК, но тогда он должен прийти к нам уведомлением, чтобы заказ закрылся.

## 24. TLS-сертификаты: сделать до деплоя

Источник: страница «Установка TLS-сертификатов» (сама инструкция по установке мне не пришла; шаги ниже собраны из документации Сбера и RuStore, помечено).

### Что требует банк

- Раньше API Т-Банка использовали сертификаты глобальных удостоверяющих центров. Банк переходит на сертификаты **Национального удостоверяющего центра Минцифры России (Russian Trusted CA)**, на переходный период используется ещё **Trust Asia**.
- **На серверах интеграции должны быть установлены оба корневых сертификата.**
- Сертификат Минцифры **не входит в доверенные хранилища** большинства ОС и языковых рантаймов, поэтому без ручной установки запросы будут завершаться **ошибкой проверки TLS**, и оплаты перестанут проходить. Trust Asia в ряде систем уже есть, но наличие нужно проверить.

### Как поставить (не первоисточник: инструкции Сбера и RuStore)

Официальные файлы Минцифры (Госуслуги):
- корневой: `https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt`
- выпускающий: `https://gu-st.ru/content/lending/russian_trusted_sub_ca_pem.crt`

Для Linux (Debian/Ubuntu):
```bash
sudo mkdir -p /usr/local/share/ca-certificates/russian-trusted
sudo curl -o /usr/local/share/ca-certificates/russian-trusted/russian_trusted_root_ca.crt \
  https://gu-st.ru/content/lending/russian_trusted_root_ca_pem.crt
sudo curl -o /usr/local/share/ca-certificates/russian-trusted/russian_trusted_sub_ca.crt \
  https://gu-st.ru/content/lending/russian_trusted_sub_ca_pem.crt
sudo update-ca-certificates
grep -c "Russian Trusted" /etc/ssl/certs/ca-certificates.crt   # должно быть больше 0
```

⚠ **Python использует собственное хранилище.** `httpx` и `requests` по умолчанию берут корневые сертификаты из пакета `certifi`, а не из системного хранилища, поэтому `update-ca-certificates` сам по себе **не поможет**. Варианты:
1. Переменная окружения `SSL_CERT_FILE=/etc/ssl/certs/ca-certificates.crt` (для `requests` `REQUESTS_CA_BUNDLE`) в окружении сервиса (unit-файл или `.env`).
2. Явный контекст в коде:
```python
import ssl, certifi, httpx

def tbank_client(ca_bundle: str | None = None) -> httpx.AsyncClient:
    ctx = ssl.create_default_context(cafile=certifi.where())
    if ca_bundle:                       # /etc/ssl/certs/ca-certificates.crt или файл с Russian Trusted
        ctx.load_verify_locations(cafile=ca_bundle)
    return httpx.AsyncClient(verify=ctx, timeout=30)
```
Путь к бандлу вынести в настройку (например `TBANK_CA_BUNDLE`).

Проверка:
```bash
openssl s_client -connect securepay.tinkoff.ru:443 -servername securepay.tinkoff.ru </dev/null 2>/dev/null | openssl x509 -noout -issuer
curl -sS -o /dev/null -w "%{http_code}\n" https://securepay.tinkoff.ru/v2/GetState
python3 -c "import httpx; print(httpx.get('https://securepay.tinkoff.ru').status_code)"
```
Если `curl` проходит, а Python падает с `CERTIFICATE_VERIFY_FAILED`, значит дело в хранилище Python (пункт выше).

⚠ Не отключать проверку (`verify=False`). Установить сертификаты нужно **на каждом сервере** (и в образе, если запуск в контейнере), и повторить после переустановки ОС.

## 25. Подключение: порядок и что это значит для платформы

Источник: страница «Начало работы». Интернет-эквайринг принимает платежи «на сайте, в приложении, мессенджерах, соцсетях, по электронной почте и СМС». Способы оплаты: карта, СБП, T-Pay, SberPay, Mir Pay, Alfa Pay, цифровой рубль, «Долями».

### Чек-лист для приёма платежей через сайт, приложение или чат

1. Ознакомиться с понятием интернет-эквайринга.
2. Изучить рекомендации и подготовиться.
3. Выбрать интеграцию.
4. Оставить заявку на подключение: **со счётом в Т-Банке** через чат в личном кабинете Т-Бизнес, **со счётом в другом банке** через сайт Т-Банка.
5. Заполнить анкету о бизнесе (есть отдельные рекомендации для компании и для ИП).
6. Создать интернет-магазин в ЛК интернет-эквайринга.
7. Настроить оплату для выбранной интеграции (раздел 22).
8. Подключить онлайн-кассу.
9. Настроить интеграцию онлайн-кассы с эквайрингом.
10. Настроить тестовый терминал.
11. Протестировать приём платежей и формирование чеков.
12. Дождаться завершения всех проверок.
13. Провести первый платёж.

Есть отдельный чек-лист для выставления счетов (без интеграции).

### Что из этого следует для Bot Factory

- Подключение оформляется **на каждый бизнес отдельно** (компания или ИП): заявка, анкета, магазин, касса. Значит, при схеме «продавец подключает свой терминал» (как у ЮKassa с Basic-авторизацией) каждому продавцу нужно пройти этот путь самому, а в нашей документации для продавцов описать шаги 4–11.
- **Мессенджеры названы допустимым каналом**, так что Telegram-бот без сайта в принципе подходит. Нужен ли адрес сайта в анкете или при настройке терминала, страница не говорит: уточнить в анкете и у менеджера.
- Страница описывает подключение конкретного бизнеса. **Схему «один терминал платформы принимает деньги за многих продавцов»** она не покрывает. В методах есть параметр `Shops` «для маркетплейсов», то есть такой режим есть, но требует отдельных условий банка. До согласования с банком держимся схемы «терминал продавца».
- Шаги 8–11: **онлайн-касса обязательна** к подключению, чеки и тест чеков входят в проверки перед боевым платежом.
- FAQ «Подключение онлайн-кассы»: **ККТ подключается до начала тестирования**, интеграцию кассы с эквайрингом настраивает мерчант, **чеки генерируются автоматически только после настройки этой интеграции**.

## 26. Возмещения и реестры

Источник: страница «Возмещения и реестры».

### Сроки возмещений

Возмещение — пополнение расчётного счёта на сумму всех операций за **один календарный день**.

| Способ | Счёт в Т-Банке | Счёт в другом банке |
|---|---|---|
| Карты, T-Pay, SberPay, Mir Pay, Alfa Pay | на следующий день (ежедневно) | до 3 календарных дней |
| СБП | по умолчанию сразу после оплаты; с опцией «Единое возмещение по СБП» — на следующий день общей суммой | то же |
| Цифровой рубль | отдельной суммой на счёт цифрового рубля | |
| «Долями» | ежедневно отдельной суммой | |

### Типы операций в возмещении и реестре

| Тип | Что это | Знак |
|---|---|---|
| `Debit` | оплата | + |
| `Credit` | возврат | − |
| `CancelRefund` | отмена возврата | + |
| `Chargeback`, `2Chargeback` | опротестование (арбитражное) эмитентом | − |
| `Chargeback_Reversal`, `2Chargeback_Reversal` | отмена опротестования | + |
| `CR_Chargeback` | возврат операции `Refund` от эмитента (карта или договор закрыты) | + |
| `Representment` | обратное опротестование `Chargeback` банком | + |
| `Representment_Reversal` | отмена обратного опротестования `2Chargeback` | − |
| `ServiceFee` | сервисный сбор | − |
| `AUTH_FAIL` | неуспешная авторизация: операция в расчёте не участвует, удерживается только комиссия | — |
| `CreditClientCorrection`, `CreditCorrection` | ручные корректировки / списание претензии покупателя | − |
| `DebitClientCorrection`, `DebitCorrection` | то же в плюс | + |

### Формат реестра

Текстовый файл в кодировке **Win CP-1251**, разделитель полей `;`, одна строка — одна операция, конец строки CR/LF. Поля:

1. Порядковый номер.
2. Маскированный номер карты или телефона.
3. Платёжная система: Visa, MC, Mir, SBP, T-Pay, SberPay, AlfaPay.
4. **Номер заказа** (цифры и буквы, без спецсимволов, до 256 знаков), то есть наш `OrderId`.
5. Дата операции `DD.MM.YYYY`.
6. Время `HH:MM:SS`.
7. Временная зона (MSK).
8. Код авторизации (6 знаков; для СБП 32-значный номер).
9. Код терминала.
10. Дата обработки.
11. Дата перечисления.
12. Сумма операции в рублях (разделитель точка).
13. Комиссия банка; 13.1 — комиссия за фискализацию (может отсутствовать).
14. **К перечислению** (после комиссии).
15. Тип операции (таблица выше).
16. RRN (кроме СБП).
17. **Payment ID** (номер операции банка, наш `PaymentId`).
18. Название терминала (4–20 латинских символов).
19. Тип карты: РФ (Dom) или иностранная (Int).
20. `DATA`: параметры из `DATA` метода `Init`, ключи `Paymentpurpose`, `Order_number`, `Email`, `Name`, `Phone`, `S_lastname`, `S_firstname`, `S_middlename`, `Number`, `mfoAgreement`.
21. Описание (`Description` из `Init`).

### Что это даёт платформе

- **Сверка:** сопоставлять строки реестра с нашими платежами по `PaymentId` (поле 17) и `OrderId` (поле 4), проверять сумму и тип операции.
- Чтобы в реестре был наш идентификатор заказа, передавать его в `OrderId` (только буквы и цифры) и/или `DATA.Order_number`, понятное `Description`.
- **Чарджбэки:** строки `Chargeback`, `2Chargeback` (минус) и их отмены (плюс) показывают спор. Платформа может помечать такой платёж как оспоренный и уведомлять продавца.
- Реестры формирует банк, скачиваются в ЛК. Получение реестра по API на странице не описано.
