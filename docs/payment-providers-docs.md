## 1. Stripe

Источники: https://docs.stripe.com/checkout/fulfillment, https://docs.stripe.com/webhooks.md **[офиц]**

### Процесс оплаты

1. Сервер создаёт Checkout Session (mode payment или subscription).
2. Клиент платит на странице Stripe.
3. Stripe шлёт вебхук. Выдавать доступ и товар надо по вебхуку, а не по возврату на return_url, потому что клиент может не дойти до вашей страницы.
4. Дополнительно можно запускать ту же функцию выдачи на странице возврата. В return_url ставится плейсхолдер `{CHECKOUT_SESSION_ID}`.

### Функция fulfill (по доке)

- Должна быть безопасна при многократном и параллельном вызове с одним session id.
- Берёт Session по ID через API с развёрнутыми `line_items`.
- Проверяет `payment_status`. Выдавать можно, если он не `unpaid`.
- Выполняет выдачу и записывает, что для этой сессии она сделана.

### События

| Событие | Когда |
|---|---|
| checkout.session.completed | клиент заплатил (для мгновенных способов) |
| checkout.session.async_payment_succeeded | отложенный способ оплаты успешно завершился позже |
| checkout.session.async_payment_failed | отложенная оплата не прошла; Stripe рекомендует обрабатывать |

Для отложенных способов (например ACH) `completed` приходит до фактического получения денег. Проверять надо именно `payment_status`.

### Подпись вебхука

- Заголовок `Stripe-Signature`: `t=<timestamp>,v1=<подпись>[,v0=…]`.
- Алгоритм: HMAC-SHA256. Ключ — секрет эндпоинта `whsec_…`. Сообщение: `<timestamp>` + `.` + сырое тело запроса.
- Схемы кроме `v1` игнорировать. `v0` — фиктивная для тестовых событий.
- Сравнивать за константное время. Проверять давность timestamp (в библиотеках по умолчанию 5 минут). Значение допуска 0 отключает проверку.
- Нужно сырое тело запроса. Любая обработка тела ломает проверку.
- Секрет у каждого эндпоинта свой, у test и live разный. При ротации секрета до 24 часов действуют два секрета, и приходит по подписи на каждый.
- Рекомендация Stripe: использовать и подпись, и allowlist IP (https://docs.stripe.com/ips).

### Ответ и доставка

- Нужен быстрый 2xx до тяжёлой логики. Редирект 3xx считается ошибкой. Только TLS 1.2 и 1.3.
- Автоповторы: до 3 дней с экспоненциальной паузой в live; в sandbox 3 раза за несколько часов.
- Ручной повтор: из Dashboard до 15 дней, через CLI до 30 дней.
- Порядок событий не гарантирован. Дубли возможны, поэтому хранить `event.id`. Иногда создаются два разных Event, тогда сравнивать `data.object.id` + `type`.
- Можно зарегистрировать до 16 эндпоинтов. Рекомендуют слушать только нужные события и обрабатывать их через очередь.

### Тест

Карта `4242 4242 4242 4242`, любой будущий срок, любой CVV. Локально: `stripe listen --forward-to localhost:4242/webhook`.

### НЕ СОБРАНО

События подписок (`invoice.paid` и др.), возвраты и `charge.*`, `checkout.session.expired`, валюты без дробной части, KZT в Checkout, Adaptive Pricing.

## 2. Crypto Bot (Crypto Pay API)

Источник: https://help.send.tg/en/articles/10279948-crypto-pay-api **[офиц, прочитано целиком]**

Актуальная версия API: **1.5.2 (18 марта 2026)**. В ней повторы вебхука увеличены до 3 суток и 17 попыток, а при полном отсутствии ответа вебхук приложения отключается автоматически.

### Доступ

- Токен приложения из @CryptoBot (@CryptoTestnetBot для тестнета): Crypto Pay → Create App.
- Заголовок: `Crypto-Pay-API-Token: <токен>`.
- URL: `https://pay.crypt.bot/api/<метод>`. Только HTTPS, UTF-8, GET и POST.
- Параметры можно слать query-строкой, JSON, urlencoded или multipart.
- Ответ всегда с булевым `ok`. При `true` данные в `result`, иначе описание в `error`.
- Хост тестнета на офиц. странице в извлечённом тексте не отобразился. Не первоисточник (npm SDK): `testnet-pay.crypt.bot`.

### createInvoice

| Поле | Описание |
|---|---|
| currency_type | `crypto` (по умолчанию) или `fiat` |
| asset | обязательно при crypto: USDT, TON, BTC, ETH, LTC, BNB, TRX, USDC |
| fiat | обязательно при fiat: USD, EUR, RUB, BYN, UAH, GBP, CNY, KZT, UZS, GEL, TRY, AMD, THB, INR, BRL, IDR, AZN, AED, PLN, ILS |
| accepted_assets | только для fiat, список через запятую; по умолчанию все |
| amount | **строка с дробным числом**, например `125.50` (не минорные единицы) |
| swap_to | попытка конвертации после оплаты (USDT, TON, TRX, ETH, SOL, BTC, LTC) |
| description | до 1024 символов |
| hidden_message | до 2048 символов |
| paid_btn_name + paid_btn_url | кнопка после оплаты: viewItem, openChannel, openBot, callback; URL обязателен, если указано имя |
| payload | любые данные до 4 КБ (ID пользователя/платежа) |
| allow_comments, allow_anonymous | по умолчанию true |
| expires_in | секунды, 1–2678400 |

### Ссылка на оплату

- Использовать **`bot_invoice_url`**. Поле **`pay_url` объявлено устаревшим** (с версии 1.2).
- Дополнительно: `mini_app_invoice_url` (Mini App) и `web_app_invoice_url` (веб-версия).

### Поля и статусы Invoice

- `status`: `active`, `paid`, `expired`.
- После оплаты: `paid_at`, `paid_asset`, `paid_amount`, `paid_usd_rate`, `fee_asset`, `fee_amount`. Поля `fee` и `usd_rate` в вебхуке устарели.
- Для фиатных счетов в оплаченном состоянии: `paid_asset`, `paid_amount`, `paid_fiat_rate`.
- `payload` возвращается как передан.

### Получение оплаты

Два способа:

1. Опрос `getInvoices` (фильтры asset, fiat, invoice_ids, status=active|paid, offset, count 1–1000, по умолчанию 100).
2. Вебхук.

### Вебхук

- Включение: @CryptoBot → Crypto Pay → My Apps → приложение → Webhooks → Enable Webhooks, затем HTTPS URL.
- POST с JSON: `update_id` (**не уникален**), `update_type` (сейчас `invoice_paid`), `request_date` (ISO 8601), `payload` (объект Invoice).
- Подпись: заголовок `crypto-pay-api-signature` = hex от HMAC-SHA256 **всего тела запроса (неразобранной JSON-строки)**, ключ = **SHA256-хеш токена приложения** (бинарный дайджест).
- Рекомендовано дополнительно проверять давность `request_date`.
- Альтернативная защита из доки: секретный путь в URL, например `/<токен>`.
- Повторы: до 17 раз за 3 суток, интервал от 10 секунд до 8 часов. После полной неудачи вебхуки приложения отключаются, владелец получает уведомление, и включать надо вручную.
- Пример в доке считает подпись от `JSON.stringify(body)`. Надёжнее брать сырые байты запроса: пересериализация может отличаться.

### Прочее

- Есть allowlist IP в Security приложения.
- `transfer` выключен по умолчанию для новых приложений. Для идемпотентности есть `spend_id` (до 64 символов).

## 3. Telegram Stars (XTR)

Источник: https://core.telegram.org/bots/payments-stars **[офиц]**. Параметры createInvoiceLink и pre_checkout взяты из зеркал Bot API (документация aiogram) **[не первоисточник, но дословно повторяют Bot API]**.

### Процесс

1. `sendInvoice` (или `createInvoiceLink`) с `currency: "XTR"`, `provider_token` пустой.
2. Telegram присылает update `pre_checkout_query`.
3. Бот отвечает `answerPreCheckoutQuery` **в течение 10 секунд**, иначе транзакция отменяется. При отказе стоит указать понятную причину, Telegram покажет её.
4. После успешной оплаты приходит сообщение `successful_payment`. **Выдавать товар можно только после него**: ответ на pre_checkout сам по себе оплату не гарантирует.
5. Сохранить `telegram_payment_charge_id` из SuccessfulPayment, он нужен для возврата.

### Прочее по доке

- В pre_checkout_query приходят `currency`, `total_amount` (целое число) и `invoice_payload`. Сумму и payload стоит сверять с заказом.
- Дробных Stars нет. Для Stars в `prices` ровно один элемент.
- Возврат: метод `refundStarPayment`.
- Подписки: `subscription_period` пока всегда **2592000** (30 дней), валюта обязательно XTR.
- Чтобы получать pre_checkout_query через вебхук, нужно включить его в `allowed_updates` (статья на Хабре, не первоисточник).
- Тест: тестовая среда Telegram (https://core.telegram.org/bots/features#testing-your-bot).
- Перед запуском Telegram требует: ответ на команду /terms, поддержка клиентов, обработка `/paysupport` для споров и ответственность владельца бота за диспуты и чарджбэки.
- Для цифровых товаров внутри Telegram разрешён только XTR.

### НЕ СОБРАНО

Лимит цены подписки, `editUserStarSubscription`, поведение продлений (повторные successful_payment и их признаки).

## 4. ЮKassa

Источники: https://yookassa.ru/developers/using-api/webhooks, https://yookassa.ru/developers/payment-acceptance/getting-started/payment-process **[офиц]**

### Основы

- API v3, базовый адрес `https://api.yookassa.ru/v3`, авторизация Basic `shop_id:secret_key` (не первоисточник для адреса и Basic; в офиц. примерах curl используется `-u`).
- На каждый POST нужен ключ идемпотентности (`Idempotence-Key`), подойдёт любое случайное значение.

### Создание платежа

Тело запроса: `amount {value: "100.00", currency}` (строка с двумя знаками), `capture` (true по умолчанию, одностадийный), `confirmation {type: redirect, return_url}`, `description`, `metadata` (возвращается без изменений).

В ответе платёж в статусе `pending` и `confirmation.confirmation_url`, куда нужно перенаправить клиента.

### Сценарии подтверждения

Redirect, External, QR-код, Embedded (виджет), Mobile application. Срок подтверждения зависит от способа оплаты. Если не успел, платёж отменяется с причиной `expired_on_confirmation`.

### Статусы

| Статус | Значение |
|---|---|
| pending | создан, ждёт действий клиента (может зависеть от чека при сценарии «сначала чек, потом платёж» на сторонней кассе) |
| waiting_for_capture | оплачен и заморожен (двухстадийный); решение за вами |
| succeeded | завершён, финальный и неизменяемый |
| canceled | отменён, финальный |

- Последовательность статусов не меняется, но часть может быть пропущена.
- Двухстадийный платёж: `capture: false`. Окно на списание от 2 часов до 7 дней (точное время в `expires_at`), иначе отмена с причиной `expired_on_capture`.
- Списание: POST `/payments/{id}/capture` (пустое тело для полной суммы, `amount` для частичной). Остаток вернётся клиенту.
- Отмена: POST `/payments/{id}/cancel`, только из `waiting_for_capture`. Из `succeeded` делается возврат.

### Уведомления

- События: `payment.waiting_for_capture`, `payment.succeeded`, `payment.canceled`, `refund.succeeded` (плюс события выплат, сделок, `payment_method.active`).
- Настройка для Basic-авторизации: личный кабинет → Интеграция → HTTP-уведомления. Для OAuth (партнёрская программа): только через API, `POST /webhooks`.
- Требования к URL: HTTPS, порт 443 или 8443, TLS 1.2+, сертификат любой (в том числе самоподписанный).
- Тело: `{type: "notification", event, object}`. `object` содержит данные на момент события.
- Ответ: **HTTP 200**, тело и заголовки игнорируются. Любой другой код — невалидный ответ, доставка повторяется **в течение 24 часов** с момента события.
- Проверка подлинности (по доке): сверить статус объекта через API **или** проверить IP отправителя. Список IP: 185.71.76.0/27, 185.71.77.0/27, 77.75.153.0/25, 77.75.156.11, 77.75.156.35, 77.75.154.128/25, 2a02:5180::/32. Подписи у уведомлений нет.

### НЕ СОБРАНО

Объект `receipt` и обязательность чека 54-ФЗ, автоплатежи и сохранение способа оплаты, возвраты, тестовый магазин, «Мир». Страницы есть в документации: `/developers/payment-acceptance/receipts/54fz/basics`, `/scenario-extensions/recurring-payments/basics`, `/after-the-payment/refunds`, `/testing-and-going-live/testing`.

## 5. Т-Банк (Tinkoff Acquiring)

Охват слабый. Первоисточник по ссылке из описания SDK: https://developer.tbank.ru/eacq/api (сам не открывал).

Что видно в не первоисточниках (PyPI-обёртка tbank-securepay, модуль mspTBank):

- Методы: Init, FinishAuthorize, Confirm, Cancel, GetState, CheckOrder.
- Хост API в обёртке: `securepay.tinkoff.ru`; тестовый контур: `rest-api-test.tinkoff.ru/v2`.
- Подпись `Token` для запросов с вложенными объектами (Receipt, DATA) строится по другим правилам. Обёртка учитывает только плоские поля верхнего уровня. Это точка риска для Init с Receipt.
- Чеки 54-ФЗ идут через `Receipt` в Init, Confirm и Refund.
- Двухстадийная схема: `PayType = T`, после статуса AUTHORIZED нужен Confirm; одностадийная завершается статусом CONFIRMED.
- `NotificationURL` можно передать в Init.

### НЕ СОБРАНО

Точная формула Token (какие поля входят, как с булевыми), формат ответа на уведомление, список статусов, актуальный домен API, рекуррент.

## 6. CloudPayments

Источник: https://developers.cloudpayments.ru **[офиц, прочитана первая часть страницы до раздела уведомлений]**

### Основы API

- Адрес: `https://api.cloudpayments.ru`. Авторизация HTTP Basic: логин Public ID, пароль API Secret. Неверные данные дают HTTP 401.
- Запросы POST, тело `key=value` или JSON. Ответ JSON с `Success` и `Message`.
- **Идемпотентность**: заголовок `X-Request-ID`; результат хранится 1 час.
- Лимит одновременных запросов: 5 для тестовых терминалов, 30 для боевых, дальше HTTP 429.
- Сумма: число с точкой, до 2 знаков, минимум 0.01. Валюта по умолчанию RUB.
- Контроль суммы нужно делать самостоятельно: **Check** до оплаты и **Pay** после.
- Карты: Visa, MasterCard, МИР (виджет определяет МИР автоматически). Есть Mir Pay, SberPay, T-Pay, СБП и другие.

### Схемы оплаты

- Single (одностадийная) и Dual (двухстадийная). После авторизации у ТСП до 7 дней (зависит от типа карты) на подтверждение, иначе автоотмена.
- Отмена возможна только при двухстадийной схеме; возврат всегда привязан к оплате (полный или частичный).
- Методы: `payments/cards/charge` и `/auth` (по криптограмме), `payments/tokens/charge` и `/auth` (по токену), `payments/cards/post3ds` (3-D Secure).

### Токен карты и рекуррент

- Токен возвращается в Pay-уведомлении и в ответе API. В виджете для этого `tokenize: true`; в API параметр `SaveCard` работает при включённой настройке «Сохранение токена карты» в ЛК.
- Токен работает только на терминале, где он получен.
- В `tokens/charge` обязательны `AccountId`, `Token`, `TrInitiatorCode` (0 — инициировал ТСП, 1 — клиент). Если инициатор ТСП, указывается ещё `PaymentScheduled` (0/1).
- Подписки CloudPayments: интервал Day/Week/Month. При неудаче повтор через сутки, после трёх неудач подряд подписка отменяется. Интервал между платежами не более года.
- В виджете для подписки нужен `userInfo.accountId`, настройки в объекте `recurrent` (period, interval, maxPeriods, amount, startDate, receipt).

### Уведомления

Типы: Check, Pay, Fail, Confirm, Refund, Recurrent, Cancel.

Не первоисточник (модуль для MiniShop3): подпись приходит в заголовке `X-Content-HMAC`, это Base64 от HMAC-SHA256 сырого тела, ключ API Secret; адрес должен открываться по HTTPS без редиректа 301.

### НЕ СОБРАНО

Раздел «Уведомления» целиком (поля, ответы, коды Check), `Content-HMAC` vs `X-Content-HMAC`, `payments/find`, `orders/create` (поле со ссылкой; в SDK методы `orders/create` и `orders/cancel` существуют), статусы операций.

## 8. Robokassa

Источники: https://docs.robokassa.ru/pay-interface/, https://docs.robokassa.ru/script-pay, https://docs.robokassa.ru/kz/quick-start **[офиц, фрагменты]**

- Страница оплаты: `https://auth.robokassa.ru/Merchant/Index.aspx`.
- Подпись запроса `SignatureValue` строится из строки `MerchantLogin:OutSum:InvId[:модификаторы]:Пароль#1[:Shp_*]` настроенным в кабинете методом хеширования (в примерах MD5).
- Если передаётся `Receipt`, он входит в строку подписи между InvId и паролем. Пример из доки: `login:sum:invid:receipt:password1:Shp_item=…`.
- Пользовательские параметры `Shp_*` добавляются в конец через двоеточие в виде `Shp_имя=значение` (в примере: `Shp_login=Vasya:Shp_oplata=1`).
- В примерах встречаются и `InvId`, и `InvoiceID`. Сверить, какое имя ждёт эндпоинт.
- Для произвольной суммы в форме используется `FreeOutSum` вместо `OutSum` (ответ на Хабр Q&A, не первоисточник).
- Quick-start: ResultURL должен быть доступен из интернета и возвращать `OK`. В кабинете есть тестовый режим.

### НЕ СОБРАНО

Формула подписи ResultURL (Пароль #2), SuccessUrl2/FailUrl2, `IsTest` и тестовые пароли, точный формат ответа `OK{InvId}`, рекуррент `/Merchant/Recurring`, возвраты, требования к чеку.

## 15. Click (Узбекистан)

Источники: https://docs.click.uz/en/click-api-request/, https://docs.click.uz/en/?p=9 **[офиц]**

### Схема

Click шлёт на ваш сервер два запроса: **Prepare** (action = 0) и **Complete** (action = 1). Complete после успешного Prepare приходит не повторно.

### Подпись `sign_string` (MD5)

- Prepare: `md5(click_trans_id + service_id + SECRET_KEY + merchant_trans_id + amount + action + sign_time)`
- Complete: `md5(click_trans_id + service_id + SECRET_KEY + merchant_trans_id + merchant_prepare_id + amount + action + sign_time)`

Формат `sign_time` в PHP-библиотеке (не первоисточник): `YYYY-MM-DD HH:mm:ss`.

### Формат ответа

JSON: `error` (0 — успех), `error_note`, `click_trans_id`, `merchant_trans_id`, а также `merchant_prepare_id` (для Prepare) или `merchant_confirm_id` (для Complete).

### Коды ошибок, которые возвращает ваша система

| Код | Смысл |
|---|---|
| 0 | успех |
| -1 | ошибка проверки подписи |
| -2 | неверная сумма |
| -3 | действие не найдено |
| -4 | уже оплачено (повторная попытка подтвердить или отменить подтверждённую транзакцию) |
| -5 | пользователь или заказ не найден |
| -6 | транзакция не найдена (проверка `merchant_prepare_id`) |
| -7 | не удалось обновить данные пользователя |
| -8 | ошибка в запросе от Click |
| -9 | транзакция отменена (повторная попытка подтвердить или отменить отменённую) |

Если Click присылает отрицательный `error`, ваша система должна отменить платёж у себя и вернуть `-9`.

### НЕ СОБРАНО

Требование «всегда HTTP 200» (в прочитанных страницах не нашёл), Merchant API (проверка статуса, возвраты).

## 16. Payme / Paycom (Узбекистан)

Источник: https://developer.help.paycom.uz **[офиц, отдельные страницы методов и песочницы]**

Merchant API (JSON-RPC): запросы приходят от Payme на ваш эндпоинт.

### Методы

| Метод | Суть |
|---|---|
| CheckPerformTransaction | можно ли провести платёж; `amount` в **тийинах**, `account`; при успехе результат `allow` |
| CreateTransaction | создаёт транзакцию; если уже создана, делается базовая проверка и возвращается результат |
| PerformTransaction | зачисляет средства, заказ становится «оплачен»; ответ `transaction`, `perform_time`, `state` (2) |
| CancelTransaction | отмена |
| CheckTransaction, GetStatement | описаны в доке, детали не читал |

### Правила реализации

- Если счёт плательщика не найден, возвращать ошибку из диапазона -31050…-31099.
- Сумма платежа проверяется на соответствие сумме выставленного счёта.
- При сбое любой из задействованных систем возвращать -32400 (системная ошибка).
- **Отмена по таймауту через 12 часов** (43 200 000 мс) с момента создания транзакции в Payme Business.
- В ошибках по `account` поле `message` локализованное и обязательное, а `data` содержит название субполя account.

### Коды ошибок

| Код | Смысл |
|---|---|
| -32700 | ошибка парсинга JSON |
| -32600 | нет обязательных полей или неверные типы |
| -32400 | системная ошибка |
| -31001 | неверная сумма |
| -31003 | транзакция не найдена |
| -31008 | невозможно выполнить операцию (см. диаграмму состояний) |
| -31050…-31099 | ошибки ввода `account` |

### Песочница

- На CheckPerformTransaction и CreateTransaction Payme проверяет, что вы возвращаете -31001 для неверной суммы и -31050…-31099 для неверного кода заказа.
- Запросы CreateTransaction, PerformTransaction, CancelTransaction **отправляются дважды**, и повторный ответ должен **совпадать** с первым (идемпотентность).

### НЕ СОБРАНО

Basic-авторизация (шаблон kolesa-team, не первоисточник, указывает ключ из кабинета мерчанта как пароль), GetStatement, коды -31007 и -31099, поле `detail` для фискального чека, тестовый кабинет.

## 17. LiqPay (Украина)

Источники: https://www.liqpay.ua/documentation/en/api/callback, https://www.liqpay.ua/documentation/en/api/information/status/doc **[офиц]**

- Callback: POST на `server_url` с полями `data` и `signature`.
- `data` = base64 от JSON с параметрами.
- `signature` = `base64( sha1( private_key + data + private_key ) )`, бинарный SHA-1. Сервер должен пересчитать подпись и сравнить с пришедшей.
- Актуальный статус можно запросить Payment Status API (`action = status`) в любой момент, не дожидаясь callback.
- Подпись для запросов к API считается так же.
- Статусы из офиц. фрагмента: `success` (успешный платёж), `wait_secure` (платёж на проверке), `reversed` (возврат), `subscribed` (подписка оформлена), `unsubscribed` (подписка деактивирована). Статусы `failure`, `sandbox`, `hold_wait` в офиц. фрагменте не попали. Не первоисточник: `sandbox` — тестовый платёж, `hold_wait` — деньги заморожены.
- Не первоисточник: server-to-server вызовы (`status`, `refund`, `hold_completion`) идут с `version=3`; и холд-отмена, и возврат списанного возвращают `reversed`.
- Checkout: `https://www.liqpay.ua/api/3/checkout`; запросы API: `/api/request` (по примерам SDK).

### НЕ СОБРАНО

Подписки и продления, формат `order_id` регулярных списаний, полный список статусов с `failure` в офиц. источнике.
