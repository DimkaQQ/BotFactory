# Живые тесты касс: что нажать, что ждать, что смотреть в базе

Чек-лист на ручной прогон перед боем и после любых правок в `app/services/payments/`.
Лежит рядом с кодом и меняется вместе с ним: поменял адаптер — поправь его раздел здесь.

> **Статус знаний.** Всё ниже выведено из кода адаптеров и из выжимки документации
> (`docs/payment-providers-docs.md`). **Ни одна касса не проверена на живом шлюзе** — для этого
> файл и нужен. Места, где поведение шлюза не подтверждено, помечены ⚠: если живой тест покажет
> другое, правь адаптер и этот файл вместе.

## 0. Общее

### 0.1. Как устроен прогон

1. В конструкторе: бот → «Оплата» → выбрать кассу → заполнить поля → **оставить «Тестовый режим»
   включённым** (он включён по умолчанию; у кассы без тестового режима — Stars, «по ссылке» — этой
   галочки нет).
2. Блок «Оплата» с ценой (для касс на тенге/сумах — в их валюте, см. «Валюты» в разделе кассы) и
   блок «Выдача» после него.
3. Открыть бота **не с аккаунта владельца** (владелец видит чужие подсказки), нажать «Оплатить».
4. Оплатить тестовым способом кассы, дождаться вебхука (адрес: `https://<домен>/webhook/pay/<slug>`).
5. Проверить: бот прислал выдачу **один раз**, владельцу пришло уведомление о продаже, статус и
   поля в базе совпадают с разделом кассы.

Адрес вебхука для кабинета кассы конструктор показывает под формой. У кассы с `sends_own_callback_url`
(Prodamus, LIFE PAY, Freedom Pay, LiqPay) адрес уходит в каждом счёте сам — в кабинете вписывать не
нужно. У Stars, «по ссылке» и Processing.kz вебхука `/webhook/pay/…` нет вовсе.

### 0.2. Переход в боевой режим

Только после того, как весь раздел кассы пройден в тесте: снять «Тестовый режим», заменить тестовые
ключи боевыми (где они разные) и **один раз заплатить настоящую минимальную сумму** — самому себе,
потом вернуть (раздел «Возврат»). Тестовый режим по умолчанию включён, поэтому «касса подключена»
в боевом режиме показывает отдельный признак «боевая» (`live` в `GET …/payment-settings`).

### 0.3. Запросы к базе

Подключение: `docker compose exec db psql -U botfactory botfactory`.

```sql
-- Последние платежи бота: статус, сумма в минорных единицах, id у шлюза, когда оплачен
SELECT id, invoice_no, provider, status, amount_minor, currency,
       provider_payment_id, paid_at,
       meta ->> 'delivered_at'  AS delivered_at,
       meta ->> 'refunded_at'   AS refunded_at
FROM payments
WHERE bot_id = '<BOT_ID>'
ORDER BY created_at DESC LIMIT 10;

-- Всё служебное, что адаптер записал по платежу (состояние Payme, ответы Freedom Pay, флаги)
SELECT jsonb_pretty(meta) FROM payments WHERE id = '<PAYMENT_ID>';

-- Подписки (кассы с автосписанием): режим, период, сколько периодов оплачено
SELECT id, provider, billing_mode, status, periods_paid, current_period_end,
       meta ->> 'gateway_cancel' AS gateway_cancel
FROM subscriptions WHERE bot_id = '<BOT_ID>';
```

Ожидаемые значения `status`: `pending` → `paid` → (`refunded`) либо `failed`. **Товар выдаётся только
после `paid`**, `delivered_at` заполняется после выдачи. Деньги — целые минорные единицы (990 ₽ =
`99000`).

### 0.4. Три сквозных кейса — для КАЖДОЙ кассы

**А. Повтор уведомления.** Касса повторяет вебхук, пока не получит свой ответ, поэтому повтор — норма.
Взять тело и заголовки уведомления из лога/кабинета кассы и послать ещё раз тем же запросом (или
нажать «Повторить отправку» в кабинете, если есть). Ожидаем: ответ кассе тот же; `status` остался
`paid`; `paid_at` и `delivered_at` **не изменились**; бот **не** прислал выдачу второй раз; период
подписки не сдвинулся. Если у кассы подпись — убедиться, что запрос с испорченным телом отвергается
(HTTP 4xx, либо тело-отказ у Click/Payme), а платёж остаётся `pending`.

**Б. Возврат.** Вернуть деньги в кабинете кассы. Дальше зависит от кассы (см. её раздел):
либо вебхук/повторная проверка статуса переводит платёж в `refunded` сам, либо адаптер возврат не
видит — тогда в журнале заказов нажать «Возврат» (`POST /api/bots/{bot}/orders/{id}/refund`): статус
станет `refunded`, `meta.refunded_at` заполнится, покупатель получит сообщение, доступ в закрытый
чат снимется. Деньги через нас не идут и возврат из конструктора их не двигает.

**В. Чек 54-ФЗ** (только ЮKassa, Т-Банк, Robokassa, PayMaster; у остальных чека от нас нет). Поля
кассы: «Передавать чек» (`fiscalization_enabled`), «Почта для чеков» (`fiscal_email`), система
налогообложения, ставка НДС. Чек уходит **только** при `fiscalization_enabled = 1`.
Кому: контакт покупателя (почта/телефон), если известен, иначе почта продавца. **Сейчас ни один шаг
диалога контакт покупателя не собирает**, поэтому на практике чек идёт на почту продавца — это
известное ограничение, не баг.

| Шаг | Ожидаем |
|---|---|
| Флаг пуст или `0` | Платёж создаётся без чека (в запросе нет `receipt`/`Receipt`). Кабинет кассы чека не показывает. У кассы с подключённой онлайн-кассой такой платёж может быть **отклонён кассой** — это значит, что флаг надо включить |
| Флаг `1`, почта заполнена | Чек создан; в кабинете кассы/ОФД одна позиция «услуга», полная предоплата, сумма = сумме платежа, ставка НДС как выбрана; получатель — почта продавца |
| Флаг `1`, почты нет | Платёж **не создаётся**: бот отвечает «не получилось открыть оплату», в логе `ProviderError: Чек включён, но чек некуда отправить…`; новой строки в `payments` нет; в настройках кассы — «не настроена: Почта для чеков» |
| Сумма чека ≠ суммы платежа | Невозможна по построению (чек из одной позиции на всю сумму); если увидел — это баг |
| Ставка НДС | Выбрать 22%: ЮKassa — `vat_code` 11; Т-Банк — `vat22`; Robokassa — `vat22`; PayMaster — `Vat22`. Для ЮKassa 5%/7% — осознанный отказ (коды не сверены) |

Миграция `0018` проставила флаг `1` тем кассам, у которых почта для чеков была заполнена до введения
переключателя; после неё правило одно — «по флагу».

## 1. Telegram Stars (`stars`)

- **Тест.** Тестового режима у кассы нет. Настоящие звёзды тратятся — ставь цену 1 ⭐. Альтернатива —
  тестовая среда Telegram (https://core.telegram.org/bots/features#testing-your-bot).
- **Шаги.** Блок оплаты в ⭐ (`XTR`) → «Оплатить» → Telegram показывает инвойс → оплатить.
- **Ждём.** Вебхука `/webhook/pay/stars` нет: подтверждение приходит как обновление на вебхук самого
  бота (`pre_checkout_query`, затем `successful_payment`). `status = paid`, выдача один раз.
- **База.** `provider = 'stars'`, `amount_minor` в звёздах × 100, `currency = 'XTR'`.
- **Повтор.** Тот же `successful_payment` (`telegram_payment_charge_id`) второй раз — выдачи нет.
- **Возврат.** Автоматического возврата звёзд нет (`refundStarPayment` не реализован) — вернуть
  звёзды через Telegram, затем «Возврат» в журнале заказов.
- **Подписка.** Первый платёж `is_first_recurring`; продление — `is_recurring` без `is_first`:
  период сдвигается, но **новой строки платежа нет**, а `periods_paid` растёт. ⚠ Продления проверяются
  только живьём: Telegram списывает раз в 30 дней, ускорить нельзя.

## 2. ЮKassa (`yookassa`)

- **Тест.** Тестовый магазин, секретный ключ `test_…` (кабинет → «Интеграция → Ключи API»).
  Тестовые карты — в документации ЮKassa. Адрес уведомлений вписать в кабинете («Интеграция →
  HTTP-уведомления», событие `payment.succeeded`; возвраты — `refund.succeeded`/`payment.canceled`).
- **Поля.** `shop_id`, `secret_key`; чек — см. 0.4.В.
- **Шаги.** «Оплатить» → страница ЮKassa → тестовая карта → вернуться в бота.
- **Ждём.** Уведомление `payment.succeeded`. Адаптер **не верит телу**: он сам запрашивает платёж по
  API и проверяет `status = succeeded`, `paid`, сумму и валюту. `status = paid`.
- **База.** `provider_payment_id` = id платежа ЮKassa; в `meta` — служебное; `amount_minor = 99000`.
- **Статус по кнопке.** «Я оплатил» перечитывает платёж (`supports_status_check`).
- **Повтор.** См. 0.4.А — повторное `payment.succeeded` ничего не меняет.
- **Возврат.** Вернуть в кабинете → адаптер при перечитывании видит возврат → `refunded` ⚠ (если
  событие не пришло — «Возврат» вручную). Частичный возврат заказ не отменяет.
- **Подписка (автоплатёж).** Первый платёж с `save_payment_method`; нужно, чтобы менеджер ЮKassa
  включил автоплатежи, иначе поле отвергается. Следующее списание — `charge_recurring` по
  `payment_method.id`; проверить `subscriptions.billing_mode = 'auto'`, при отказе карты —
  `failed` и сообщение подписчику «не получилось списать».

## 3. Т-Банк (`tbank`)

Сверено с `docs/tbank-docs.md`. Не проверено на живом терминале.

- **Что клиенту сделать у банка до подключения:** заявка и анкета (компания или ИП; про самозанятых и физлиц
  в документации ничего нет — уточнить у банка), магазин в ЛК, **онлайн-касса и её интеграция с
  эквайрингом**, терминал типа **«Универсальное»**, включённая «Готовая платёжная форма» с нужными способами
  оплаты, чек-лист запуска. Для подписок менеджер банка должен включить платежи по сохранённым реквизитам.
- **Тест (два способа, оба проверить):**
  1. **Боевой терминал без `DEMO` + тестовый хост** `rest-api-test.tinkoff.ru` — это наш «Тестовый режим»
     (хост выбирается автоматически; режим запоминается в `payment.meta.tbank_test`). Тестовые карты работают
     только здесь: `2201382000000013` (3DS без пароля), `2201382000000047` (3DS, пароль `1qwezxc`),
     `2200770239097761` (без 3DS), `2201382000000831` (недостаточно средств), `2201382000000005`
     (аутентификация отклонена); срок любой, CVV `123`. ⚠ `2201382000000021` в документации указана дважды.
  2. **DEMO-терминал** (Terminal Key заканчивается на `DEMO`) — работает на боевом хосте, нужен для тест-кейсов
     из ЛК («Магазины → Терминалы → Тестовый → Тестировать»). Адаптер для DEMO-терминала всегда ходит на боевой
     хост, даже в тестовом режиме.
- **TLS (до первого запроса!).** Банк переходит на сертификаты Минцифры; в контейнере их нет. Проверка:
  `docker compose exec api python -c "import httpx;print(httpx.get('https://securepay.tinkoff.ru').status_code)"`.
  Если `CERTIFICATE_VERIFY_FAILED` — `deploy/install-russian-ca.sh` (скачивает, печатает отпечатки — сверь
  с официальной страницей), `TBANK_CA_BUNDLE=/certs/russian_trusted.pem` в `.env`, пересоздать `api` и `worker`.
- **Поля.** `terminal_key`, `password`; чек — 0.4.В (`taxation`, `tax`; `vat20` больше не принимается; признак
  расчёта всегда `full_payment`).
- **Шаги.** «Оплатить» → форма банка → тестовая карта.
- **Init проверить в логе/запросе:** `OrderId` — 32 символа без дефисов; нет `PayType`; `Description` ≤ 140 знаков
  без `& < > ' "`; `NotificationURL` — наш; для подписки `Recurrent=Y`, `CustomerKey` ≤ 36 и
  `DATA.OperationInitiatorType = "1"`; для обычной оплаты `DATA` нет. ⚠ Если банк потребует `DATA` и для
  разовой оплаты (в примере доки там `"0"`) — исправить адаптер.
- **Ждём.** Уведомление с `Token`: **неподписанное или с неверной подписью отвергается** (HTTP 400, в банк мы
  не ходим), банк повторяет сам (раз в час сутки). Подписанное → мы перечитываем `GetState`, сверяем сумму и
  `OrderId`, отвечаем `OK`. `CONFIRMED` → `paid`; `AUTHORIZED` → **адаптер сам вызывает `Confirm`**
  (с тем же чеком) и верит только следующему чтению; `REJECTED`/`CANCELED`/`DEADLINE_EXPIRED`/`REVERSED`/
  `AUTH_FAIL` → `failed`; `REFUNDED`/`PARTIAL_REFUNDED` → `refunded` ⚠ (частичный возврат закрывает заказ целиком —
  решение общее для касс, пересмотреть при необходимости). При одностадийной оплате приходят два уведомления
  (`AUTHORIZED` и `CONFIRMED`) — выдача всё равно одна.
- **Двухстадийный терминал.** В ЛК: Магазины → Приём оплаты → «После подтверждения заказа». Оплатить →
  в логе `GetState → Confirm → GetState`, платёж `paid`, выдача одна. Если `Confirm` не прошёл — платёж
  остаётся `pending`, «Я оплатил» или повтор уведомления доведут.
- **База.** `provider_payment_id` = PaymentId банка; `meta.tbank_test`, `meta.tbank_receipt` (если чек),
  `meta.tbank_rebill_id` (после подписки).
- **Повтор.** 0.4.А: подписанное уведомление ещё раз → `OK`, состояние не меняется.
- **Возврат.** Вернуть в ЛК («Операции → Вернуть») → `REFUNDED` → `refunded` (сам возврат из конструктора
  не делается). ⚠ При частичном возврате с онлайн-кассой банку нужен чек с возвращаемыми позициями — это ручной
  возврат в ЛК.
- **Подписка.** Первый платёж — 3DS, карта сохраняется (в уведомлении `RebillId`; проверить
  `payment.meta.tbank_rebill_id`, `subscriptions.meta.recurring_token` есть). Продление: `Init` (с `Receipt`,
  `DATA.OperationInitiatorType="R"`, без `PayType`) + `Charge` → `CONFIRMED`. Отказ карты: сообщение по коду
  (недостаточно средств, срок карты и т.д.), платёж `failed`. Ошибка **10** — автоплатежи не включены на терминале
  («попроси менеджера»). Обрыв связи на `Charge` — повторного `Charge` нет, смотрим `GetState`.
  **Ещё проверить на DEMO:** нужен ли `AddCustomer` перед `Recurrent=Y`; идемпотентность `Charge`; что после
  `RemoveCard` старый `RebillId` отклоняется (отмена подписки сейчас карту в банке не удаляет — списания
  прекращаются только с нашей стороны).
- **Не сделано (знаем):** проверка IP банка; возврат из конструктора (`Cancel` с `ExternalRequestId`); кнопка
  «Проверить подключение»; согласие клиента на автосписания в интерфейсе (текст акцепта нужно показать до
  первого платежа подписки — требование банка).

## 4. CloudPayments (`cloudpayments`)

- **Тест.** Тестовый терминал `test_api_…` в кабинете; тестовые карты — раздел «Тестирование»
  документации (номера ⚠ не собраны — взять из кабинета). Уведомление `Pay` настроить в кабинете.
- **Поля.** `public_id`, `api_secret`. Валюты: RUB, KZT, USD, EUR, UAH.
- **Шаги.** Ссылка → виджет → тестовая карта.
- **Ждём.** Уведомление подписано HMAC (`Content-HMAC`/`X-Content-HMAC`; подходит любой из двух над
  сырым или раскодированным телом); адаптер **ещё и перечитывает** платёж по `InvoiceId` через API.
  Ответ кассе — `{"code":0}`. `Completed` → `paid`.
- **Повтор.** 0.4.А.
- **Возврат.** `Refunded`/`PartiallyRefunded` при перечитывании → `refunded`.
- **Подписка.** Режим `token`: первый платёж отдаёт токен, дальше мы списываем
  `payments/tokens/charge` с `TrInitiatorCode=0`, `PaymentScheduled=1`. ⚠ Подписки на стороне
  CloudPayments (`create_subscription`) написаны, но **не включены**; перед включением нужен живой
  тест — с каким `InvoiceId` приходят плановые `Pay`.

## 5. PayMaster (`paymaster`)

- **Тест.** `testMode = true` в запросе (тестовый платёж, не настоящие деньги) ⚠ тестовая карта
  из выжимки — не первоисточник; уточнить в кабинете.
- **Поля.** `merchant_id`, `token`; чек — 0.4.В (CamelCase-значения: `Vat22`, `FullPrepayment`, `Service`).
- **Ждём.** Уведомление на `callbackUrl` — адаптер перечитывает платёж. `Settled` → `paid`;
  `Pending`/`Confirmation` — **ещё не оплата**. Токен рекуррента — `paymentToken.id`.
- **Возврат.** `Refunded`/`PartiallyRefunded` → `refunded`.
- **Повтор.** 0.4.А. Статус по кнопке «Я оплатил» поддержан.

## 6. Robokassa (`robokassa`)

Сверено с официальным OpenAPI (`docs/robokassa-openapi.yaml`) и `docs/robokassa-docs.txt`. Не проверено на живом магазине.

- **Алгоритм хэша.** В технических настройках магазина выбирается MD5 (по умолчанию), SHA1, SHA256, SHA384, SHA512
  или RIPEMD160 — подпись надо считать тем же. Поле «Алгоритм хэша» в настройках кассы (`hash_algo`); если в
  кабинете не MD5, а поле пустое, **каждый** платёж упадёт с ошибкой 29. Проверить: тестовый платёж с тем алгоритмом,
  что выбран в кабинете.
- **Описание** — до 100 знаков без спецсимволов (чистится автоматически).
- **Тест.** Только тестовые пароли #1/#2 из «Технических настроек» и `IsTest=1`; без заполненных `test_password1/2`
  тестовый режим отказывает с понятной ошибкой. Тестовые оплаты в кабинете не видны. Валюта — только RUB.
- **ResultURL (POST, настраивается в кабинете):** подпись `OutSum:InvId:Пароль#2[:Shp_*]` тем же алгоритмом (регистр
  hex не важен); `Shp_*` берутся из уведомления по алфавиту. Пароль выбирается по режиму **этого платежа**
  (`meta.robokassa_test`). Ответ кассе — буквально `OK<InvId>`. В тестовом режиме `OutSum` приходит с двумя знаками,
  в боевом — с шестью (сумма сравнивается как число). IP Robokassa (необязательно, подпись проверяем сами):
  `185.59.216.65`, `185.59.217.65`.
- **Чек.** `Receipt` входит в подпись ссылки (один раз закодированный `urlencode`), в самой ссылке закодирован ещё
  раз; если касса отвечает ошибкой 29 — проверь кодирование. Для рекуррента чек тоже передаётся и входит в подпись.

- **Возврат.** `charge.refunded`: только при `refunded = true` платёж `refunded`; **частичный**
  возврат заказ не отменяет.
- **Подписка** (`gateway`): первый платёж создаёт Subscription; проверить `invoice.paid` на
  продлениях ⚠ (в адаптере не подтверждено).
- **Повтор.** Повторить событие из дашборда («Resend») — состояние то же.

## 17. Crypto Bot (`cryptobot`)

- **Тест.** Тестнет: бот @CryptoTestnetBot, адрес API `testnet-pay.crypt.bot` ⚠ (из SDK, не из доки);
  токен приложения — в @CryptoBot → Crypto Pay.
- **Ждём.** Вебхук `invoice_paid` с подписью (HMAC-SHA256 телом запроса, ключ — sha256 токена); `paid` по статусу счёта; сумма —
  в криптовалюте счёта. «Я оплатил» поддержан.
- **Возврат.** Не видим → вручную.
- **Повтор.** 0.4.А.

## 18. «Оплата по ссылке» (`link`) и «Тестовая оплата» (`test`)

- **link.** Вебхука нет: покупатель платит по внешней ссылке и жмёт «Я оплатил» — запрос уходит
  **владельцу**, и платёж `paid` только после его подтверждения в журнале заказов («Подтвердить»).
  Проверить: до подтверждения `status = pending`, `meta.claimed_at` заполнено, выдачи нет.
- **test.** Деньги не двигаются; **в боевом режиме выключена** и не может подтвердить оплату открытием
  ссылки. Использовать только для проверки сценария диалога.
